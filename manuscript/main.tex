\begin{abstract}

Engineering an initial metadata schema for a previously unsupported artifact type remains a largely manual knowledge engineering task despite recent advances in multimodal large language models (LLMs). Existing metadata standards describe mature vocabularies, while metadata extraction methods typically assume that an appropriate schema already exists. We present a human-in-the-loop methodology for metadata schema engineering that decomposes the process into a sequence of explicit semantic transformations connected by intermediate knowledge artifacts, enabling transparent reasoning, iterative expert review, and reproducible schema development while assigning complementary roles to multimodal LLMs and human experts. The methodology is demonstrated through the development of the Data Snapshot Metadata Schema using a representative collection of 210 data snapshots extracted from institutional documents. Beyond the resulting schema, this work contributes a repeatable methodology for engineering initial metadata schemas and argues that metadata schema engineering constitutes a distinct stage of knowledge engineering that benefits from explicit intermediate knowledge artifacts and complementary human--AI reasoning.

\end{abstract}

\section{Introduction}

Metadata provides the descriptive foundation that enables digital resources to be organized, discovered, exchanged, and reused~\citep{gilliland2008}. Well-designed metadata schemas support consistent annotation, interoperability, retrieval, provenance tracking, and downstream analytical workflows across heterogeneous information systems~\citep{metadatainteroperability2006}. For mature domains, such schemas typically emerge through years of community collaboration, iterative refinement, and the gradual convergence of expert knowledge into widely adopted metadata standards~\citep{caplan2003}.

Recent advances in document understanding and multimodal information systems have made it increasingly feasible to extract analytical artifacts embedded within documents—such as statistical tables, charts, maps, dashboards, and monitoring frameworks—as standalone information objects that can be indexed, retrieved, and managed independently of their source documents~\citep{wang2025,dy2026}. As these artifacts become standalone information objects, they require metadata describing their analytical content, structure, and context, rather than solely the bibliographic properties of the documents from which they originate~\citep{gilliland2008}. While existing metadata standards provide many relevant concepts, no single standard adequately describes the metadata required to represent the analytical semantics of many such artifact types~\citep{gilliland2008}.

Our broader research investigates one such class of artifacts, which we refer to as \emph{data snapshots}: semantically meaningful analytical artifacts extracted from institutional documents and managed as independent information objects~\citep{dy2026}. Developing a metadata extraction and retrieval pipeline for these artifacts required a metadata schema capable of describing the snapshots themselves rather than only their source documents.

Although existing metadata standards provide many concepts applicable to digital resources, they are generally designed for particular resource types or application domains rather than analytical artifacts of this kind~\citep{gilliland2008, metadatainteroperability2006}. In evaluating these standards for our use case, we found that none adequately captured the information required for data snapshots. Consequently, before metadata could be extracted automatically, the metadata schema itself had to be engineered. This revealed a more fundamental challenge: how should an initial metadata schema be systematically engineered for a previously unsupported artifact type? Developing an initial metadata schema for a previously unsupported artifact type remains largely expert-driven. The process requires discovering candidate metadata concepts from representative artifacts, consolidating semantically related concepts, refining conceptual boundaries, and translating the resulting concept inventory into an operational metadata schema through iterative expert review~\citep{greenberg2005,coyle2009applicationprofiles}. Existing research on metadata standardization, schema discovery, ontology engineering, and ontology learning provides complementary foundations for this task. The question addressed here is how those foundations can be adapted when the descriptive requirements must first be discovered from multimodal artifacts and the required endpoint is an operational metadata schema.

Recent advances in multimodal large language models (LLMs) provide an opportunity to support the exploratory stages of metadata schema development~\citep{ding2026vrdu,bian2025}. Rather than treating schema development as a single prompting task, we propose a human-in-the-loop methodology that decomposes the process into explicit semantic transformations connected by intermediate knowledge artifacts. These artifacts preserve evidence for expert review while enabling multimodal LLMs and human experts to contribute complementary forms of reasoning throughout the workflow.

We demonstrate the methodology through the development of the Data Snapshot Metadata Schema for data snapshots. The case study shows how heterogeneous metadata observations can be progressively transformed into an operational metadata schema through explicit intermediate knowledge artifacts that support transparent human–LLM collaboration. Beyond the resulting schema, the paper contributes a repeatable methodology for developing metadata schemas for previously unsupported classes of multimodal analytical artifacts.

\section{Related work}

The proposed methodology adapts established ideas from metadata profile development, schema discovery, ontology learning, knowledge graph construction, and multimodal document understanding. It integrates these strands into a workflow for deriving an operational metadata schema from the multimodal artifacts it is intended to describe. Specifically, the methodology connects independently gathered artifact evidence to a shared concept inventory and, ultimately, an operational metadata schema while preserving traceability to each source artifact.

\subsection{Metadata standards and schema development}

Metadata standards provide descriptive frameworks through which digital resources can be organized, discovered, exchanged, and preserved~\citep{gilliland2008}. Application-profile guidance further distinguishes the characterization of the resources being described, the selection and definition of metadata terms, the design of metadata records and constraints, and the documentation of usage rules~\citep{coyle2009applicationprofiles}. These activities provide a useful foundation for operational metadata schema development.

Existing metadata vocabularies nevertheless do not remove the need for application-specific design. A target artifact class may require terms drawn from several sources, locally defined terms, constraints, and usage guidance assembled into a coherent operational specification~\citep{greenberg2005,coyle2009applicationprofiles}. The problem addressed here is therefore not the absence of relevant metadata concepts, but the absence, at the outset of the work, of a directly adoptable metadata schema for data snapshots as defined in this study.

The resulting Data Snapshot Metadata Schema is presented as a dedicated operational specification for this artifact class rather than as a community standard. Standards alignment, community governance, and formal standardization are separate, longer-term processes beyond the artifact-driven development studied here.

\subsection{LLM-assisted schema discovery and ontology learning}

LLMs4SchemaDiscovery presents an iterative human-in-the-loop workflow for deriving scientific schemas from text through seed-schema construction, expert feedback, corpus expansion, and ontology grounding~\citep{sadruddin2025schemadiscovery}. Our setting differs in both input modality and workflow organization: schema evidence is derived from multimodal analytical artifacts, observations are generated independently for each snapshot, and deterministic field profiles aggregate local evidence before concepts are consolidated.

LLM-assisted ontology learning provides a second methodological foundation. LLMs4OL decomposes ontology learning into tasks such as term typing, taxonomy discovery, and non-taxonomic relation extraction~\citep{giglou2023llms4ol}. NeOn-GPT embeds LLM prompting within a staged ontology-development methodology and produces formal ontologies from domain descriptions and competency questions~\citep{fathallah2025neongpt}; its extended version adds ontology reuse together with automated verification and repair~\citep{fathallah2026extended}. OntoGenix similarly provides a structured dataset-to-ontology workflow that includes ontology planning and construction as well as mappings and RDF generation~\citep{valcalvo2025ontogenix}.

Together, these studies show how LLMs can support progressively more formal knowledge-representation tasks, from term typing and taxonomy construction to ontology reuse, verification, and repair.

Stage-wise evidence suggests that expert involvement becomes increasingly important as ontology work progresses from term extraction toward hierarchy and relation specification~\cite{ding2026ontology}. A systematic review similarly identifies broad use of LLMs across ontology-engineering activities alongside limited human evaluation and inconsistent validation practices~\cite{li2026ontologyreview}. These findings support assigning exploratory discovery and abstraction to the LLM while retaining human responsibility for conceptual boundaries, consolidation decisions, and operational schema design.

\subsection{Open schema induction and knowledge graph construction}

Open knowledge graph construction offers related patterns for discovery, definition, and canonicalization. The Extract--Define--Canonicalize framework extracts relations from text, defines candidate relations, and canonicalizes them against an existing or induced schema~\citep{zhang2024edc}. Broader surveys place these operations within LLM-supported ontology engineering, information extraction, schema induction, and knowledge integration~\citep{bian2025}. These approaches support open discovery and semantic consolidation, but primarily target relational schemas and knowledge graphs rather than an operational metadata specification for describing multimodal artifacts.

\subsection{Multimodal document understanding}

Multimodal document-understanding research provides the capabilities required to interpret combinations of text, tables, charts, layout, and other visual evidence in visually rich documents~\citep{wang2025,ding2026vrdu}. Its usual objective is to understand or extract information from documents, often with a predefined target representation. In this work, multimodal interpretation is instead used upstream to discover which metadata concepts are needed: the visual artifacts are evidence from which the descriptive representation is derived.

\subsection{Positioning of this work}

Taken together, the reviewed literature provides human-in-the-loop schema discovery, staged ontology construction, task decomposition, open schema induction and canonicalization, and multimodal artifact interpretation. This paper adapts these strands into an artifact-driven architecture for metadata schema development. The architecture analyzes snapshots independently before introducing a shared vocabulary; retains local observations rather than immediately absorbing them into an evolving schema; aggregates evidence in deterministic field profiles; separates canonical concept synthesis, expert refinement, and concept coverage assessment; and subsequently translates the refined concept inventory into an operational metadata schema. Each transformation remains traceable to the visual artifacts that motivated it.

\section{Conceptual framework}

This paper addresses the problem of developing metadata schemas for multimodal analytical artifact types that lack a dedicated operational metadata specification. Before presenting the proposed methodology, we establish the conceptual framework that underpins the remainder of the paper. In particular, we distinguish among \emph{metadata}, \emph{metadata concept inventory}, and \emph{metadata schema}. We then define how \emph{metadata schema development} is used in this paper and formulate the problem addressed by the methodology.

\subsection{Data snapshots as independent information objects}

A \emph{data snapshot} is a semantically meaningful analytical artifact extracted from a document page and treated as an independent information object~\citep{dy2026}. Examples include statistical tables, charts, maps, dashboards, monitoring frameworks, and composite analytical figures. Representative examples are provided in Appendix~\ref{appendix:datasnapshots}. Unlike document pages, data snapshots encapsulate specific analytical content and are often reused, searched, or interpreted independently of their source documents. Treating each data snapshot as an independent information object enables metadata to be assigned at the level where the analytical content is expressed, rather than inherited solely from the source document.

Conventional document-level metadata such as title, author, publication date, or organization provides valuable context about the source document but is insufficient to describe the analytical content of individual data snapshots. For example, multiple data snapshots within the same report may describe different indicators, geographic regions, populations, or time periods while sharing identical document metadata. Effective organization, retrieval, and downstream analysis therefore require metadata that describes the snapshots themselves rather than only the documents from which they were extracted.

\subsection{Conceptual distinctions}

Building on the definition of a data snapshot, we distinguish three closely related concepts that play distinct roles in the proposed workflow.

\paragraph{Metadata}

Metadata is descriptive information about a data snapshot. It consists of properties that help identify, interpret, organize, retrieve, or manage a snapshot~\citep{gilliland2008}. Examples include the analytical indicator represented, geographic coverage, temporal coverage, visualization type, source organization, and other descriptive attributes. Metadata primarily answers the question: "What does this snapshot represent?"

\paragraph{Metadata concept inventory}

A metadata concept inventory is the intermediate conceptual artifact used in this methodology. It records canonical metadata concepts together with definitions, rationales, representative discovered fields, and expert decisions to retain, merge, or exclude concepts. It supports conceptual consolidation and review before the concepts are translated into operational metadata fields. The inventory differs from an ontology in that it does not assert a class hierarchy, formal semantic relations, axioms, or instances~\citep{uschold&gruninger1996,noy&mcguinness2001}.

\paragraph{Metadata schema}

A metadata schema is an operational specification describing which metadata fields should be captured for a data snapshot together with their definitions, intended use, and annotation guidance~\citep{greenberg2005,coyle2009applicationprofiles}. It translates the refined metadata concept inventory into a record structure that can guide subsequent annotation, storage, retrieval, and extraction. In this paper, \emph{metadata schema development} denotes the full evidence-driven process of discovering, consolidating, specifying, and assessing these metadata fields.

\subsection{Scope}

The proposed methodology addresses the development of an operational metadata schema for a class of multimodal analytical artifacts that lacks a dedicated operational schema or directly adoptable metadata profile. Existing standards and vocabularies may still provide applicable terms. The task is to identify, consolidate, define, and operationalize descriptive requirements grounded in representative artifacts.

As illustrated in Figure~\ref{fig:conceptual_relationship}, the proposed methodology concludes with an operational metadata schema evaluated against held-out artifacts. Metadata extraction and downstream applications therefore fall outside the scope of this work. Subsequent activities that adapt the schema to specific technical or interoperability requirements are also outside the paper's boundary.

\subsection{Problem definition}

Schema development for established resource types can draw on mature standards, shared conventions, and accumulated domain knowledge. When an artifact class is not yet adequately characterized, its descriptive requirements cannot be assumed in advance. Defining fields solely from expert expectations or a small number of salient examples may omit less frequent properties that remain important for interpretation or discovery. The schema must therefore be grounded in evidence from representative artifacts before a shared vocabulary is fixed.

We therefore consider the following problem:

\begin{quote}
Given a representative collection of multimodal analytical artifacts for which no dedicated operational metadata schema exists, how can an operational metadata schema be systematically developed from artifact-level evidence?
\end{quote}

This problem presents four challenges. First, the relevant metadata space is initially unknown. Second, artifact-level observations are heterogeneous and local; they must be aggregated and consolidated while retaining traceability to their source artifacts. Third, the resulting concept inventory must be translated into fields, definitions, and guidance suitable for consistent use. Finally, the completed schema must be evaluated on held-out artifacts without treating every rare semantic distinction as evidence for a new field.

We address these challenges by decomposing metadata schema development into a sequence of semantic transformations connected by explicit intermediate knowledge artifacts. Multimodal LLMs support artifact interpretation, broad metadata discovery, semantic consolidation, and structured gap analysis. Human experts retain responsibility for scope, conceptual boundaries, operational schema design, and the adjudication of validation evidence.

The following section presents the proposed methodology.

\label{sec:methodology}

The methodology is intended to support early-stage schema development by combining multimodal large language models with structured knowledge engineering. Rather than replacing human judgment, it decomposes metadata schema engineering into a sequence of semantic transformations connected by explicit intermediate knowledge artifacts.

A central design principle is the decomposition of the methodology into distinct knowledge engineering stages connected by explicit intermediate knowledge artifacts. This decomposition separates semantic discovery, conceptual modeling, validation, and operational specification into explicit stages, making the engineering process transparent, reviewable, and reproducible. The proposed methodology progressively transforms metadata observations into increasingly structured knowledge artifacts, culminating in an operational metadata schema. Each workflow stage transforms one intermediate artifact into the next, enabling the engineering process to be reviewed and refined incrementally. The methodology is presented independently of the case study; implementation-specific details are deferred to Section~\ref{sec:case_study}.

\subsection{Metadata discovery}

The objective of metadata discovery is to externalize candidate metadata concepts that describe representative analytical artifacts. At this stage, the emphasis is intentionally placed on discovery breadth rather than semantic precision. Accordingly, the stage seeks to identify all potentially useful metadata, including concepts that may later prove redundant, ambiguous, or outside the scope of the final schema.

This stage begins with a representative sample of multimodal analytical artifacts drawn from the target domain. The methodology assumes that the sample captures the diversity of artifact types, reporting styles, and semantic content expected in downstream applications.

Each artifact is processed independently using a multimodal LLM, which proposes candidate metadata fields from the visual and textual content of the artifact rather than selecting from a predefined vocabulary. Independent processing serves two complementary purposes. First, it prevents early convergence toward a shared vocabulary, allowing diverse local semantic interpretations to emerge before consolidation. Second, it minimizes bias introduced by previously processed artifacts, allowing each artifact to reveal its own descriptive characteristics. Consistent with the emphasis on discovery breadth, redundancy and semantic overlap are intentional. Candidate metadata fields are therefore expected to include synonymous terminology, differing levels of abstraction, and concepts that may ultimately be excluded from the final schema.

Metadata observations are generated without human curation or filtering to preserve discovery breadth and reduce the risk of prematurely excluding useful concepts. Human involvement is therefore limited to defining the discovery objective, selecting representative artifacts, and designing the prompting strategy. The output of this stage is a collection of metadata observations describing the sampled artifacts. These observations serve as the input to field profile aggregation.

\subsection{Field profile aggregation}

The objective of field profile aggregation is to consolidate the metadata observations produced during metadata discovery into \emph{metadata field profiles}. Rather than reasoning over individual observations, subsequent stages operate on these profiles, reducing the amount of context presented to later stages while establishing metadata field profiles as the primary units of semantic reasoning.

This stage groups metadata observations referring to the same candidate metadata field into a single metadata field profile using deterministic exact-name matching, without semantic normalization or canonicalization (e.g., "geographic location" and "geographic locations" remain separate profiles). Each profile aggregates representative supporting evidence—including frequent values, example descriptions, occurrence statistics, and explanatory reasoning—providing a compact representation for subsequent ontology induction.

The output of this stage is a collection of metadata field profiles that represent the unique candidate metadata fields identified across the representative artifact collection and serve as the input to ontology induction.

\subsection{Ontology induction}

The objective of ontology induction is to transform the metadata field profiles produced during field profile aggregation into a \emph{candidate ontology} comprising canonical metadata concepts. Whereas metadata discovery emphasizes broad semantic exploration, ontology induction emphasizes semantic abstraction by identifying common concepts shared across multiple metadata field profiles.

This stage takes the metadata field profiles from the previous stage as input. Unlike field profile aggregation, which groups observations using exact field names, ontology induction consolidates field profiles representing the same underlying metadata concept into canonical metadata concepts. Distinct concepts, including infrequently occurring ones, are intentionally preserved to reduce semantic redundancy without sacrificing conceptual diversity.

To minimize the risk of incorrect semantic merges, ontology induction intentionally favors under-consolidation over premature consolidation. Concepts that remain separate can still be merged during ontology engineering, whereas concepts merged too aggressively during this stage may be difficult to recover. For example, simple plural variants such as "geographic location" and "geographic locations" would typically be consolidated at this stage, whereas the relationship between concepts such as "data type" and "format" may require human judgment.

The candidate ontology is generated by applying multimodal LLM-based semantic abstraction to the aggregated field profiles. For each canonical metadata concept, the ontology includes a definition, representative examples, and explanatory reasoning supporting the proposed consolidation. The resulting candidate ontology represents the first global conceptual model of the discovered metadata space and serves as the input to ontology engineering.

\subsection{Ontology engineering}

The objective of ontology engineering is to transform the candidate ontology produced during ontology induction into a refined ontology suitable for operational use. Whereas ontology induction emphasizes semantic abstraction, ontology engineering emphasizes conceptual correctness, scope definition, and semantic consistency. It is during this stage that the canonical metadata vocabulary is finalized.

Ontology engineering proceeds through an iterative review process in which candidate metadata concepts are evaluated individually and in relation to the ontology as a whole. Typical refinement activities include merging semantically equivalent concepts, splitting concepts that capture multiple distinct ideas, renaming concepts to improve clarity, excluding concepts that fall outside the intended metadata scope, refining definitions and examples, and clarifying conceptual boundaries between related concepts.

These refinement activities are guided primarily by semantic reasoning rather than empirical frequency. The objective is not to minimize the number of concepts, but to produce an ontology that is conceptually distinct, internally consistent, and appropriate for the intended application. A recurring consideration during ontology engineering is the distinction between descriptive metadata and extraction outputs. Candidate concepts describing values that should be extracted from analytical artifacts, rather than metadata describing the artifacts themselves, are removed from the ontology. This refinement establishes a clear conceptual boundary between metadata schema engineering and downstream metadata extraction.

Ontology engineering is guided primarily by human judgment. Multimodal LLMs may support the process by proposing alternative concept names, identifying overlapping definitions, summarizing similarities and differences between concepts, and suggesting refinements, but final decisions regarding concept merges, exclusions, definitions, and organization remain the responsibility of the human expert. The output of this stage is a refined ontology with clearly defined semantic boundaries that serves as the conceptual foundation for schema engineering.

\subsection{Ontology validation}

The objective of ontology validation is to evaluate the refined ontology produced during ontology engineering and assess whether it provides an appropriate conceptual model of the discovered metadata space. Unlike the preceding workflow stages, ontology validation does not modify the ontology or produce a new conceptual knowledge artifact. Instead, it generates validation evidence that supports subsequent human judgment regarding the adequacy of the engineered ontology.

Ontology validation is performed by assigning each metadata field profile generated during field profile aggregation to one of the predefined ontology concepts using ontology-constrained classification. This classification may be performed using a multimodal LLM or another suitable classification approach, enabling quantitative analyses of ontology behavior across the representative corpus.

The resulting concept assignments support analyses such as concept frequency distributions, corpus coverage, visualization-type coverage, identification of rare concepts, and inspection of concepts receiving unexpectedly high or low empirical support. These analyses provide evidence rather than prescribing ontology modifications. For example, infrequently occurring concepts may remain operationally important if they capture semantically distinct aspects of the artifact domain. Instead, the validation evidence informs human judgment and may motivate additional ontology refinement before proceeding to schema engineering. The output of this stage is a collection of validation evidence, including concept assignments, descriptive statistics, and related analyses characterizing the coverage and behavior of the engineered ontology.

\subsection{Optional extension: Scaling ontology engineering}

Ontology engineering relies primarily on human review. While this is practical for moderately sized ontologies, exhaustive manual inspection becomes increasingly difficult as the number of concepts grows. For larger ontologies, similarity-based analyses can provide optional decision support.

Similarity-based analyses identify relationships between metadata field profiles or ontology concepts using semantic similarity or co-occurrence. These relationships may be explored through techniques such as hierarchical clustering, community detection, or network visualization to identify groups of closely related concepts.

These analyses support human judgment by highlighting candidate concept merges, unexpected conceptual clusters, isolated concepts, or regions of the ontology requiring additional inspection. They provide complementary evidence for ontology engineering but do not replace semantic reasoning or automate ontology design decisions.

Accordingly, similarity-based analyses are treated as optional decision-support mechanisms rather than mandatory workflow stages. Their value increases with ontology size and complexity by helping focus human review on areas most likely to benefit from further inspection.

\subsection{Schema engineering}

The objective of schema engineering is to transform the refined ontology into an operational metadata schema. Whereas ontology engineering establishes a conceptually coherent representation of the metadata space, schema engineering emphasizes practical implementation by defining metadata fields suitable for annotation, storage, retrieval, and downstream metadata extraction.

Schema engineering proceeds through an iterative design process that translates canonical metadata concepts into an operational metadata specification. Typical activities include merging ontology concepts that are conceptually distinct but operationally better represented by a single metadata field, introducing metadata fields required for practical deployment, removing concepts whose implementation cost outweighs their operational value, refining field names and definitions to improve annotation consistency, organizing metadata fields into coherent semantic modules, and developing annotation guidance, examples, and scope notes for each metadata field.

Unlike ontology engineering, which seeks to establish \emph{what metadata concepts exist}, schema engineering determines \emph{how those concepts should be represented within an operational metadata specification}. Consequently, schema engineering balances semantic correctness with practical considerations including annotation consistency, usability, maintainability, and long-term deployment. These decisions often involve trade-offs that cannot be resolved through semantic reasoning alone. For example, conceptually distinct ontology concepts may be represented by a single metadata field to simplify annotation, and infrequently occurring concepts may be retained because they provide operationally important metadata.

Schema engineering is guided primarily by human judgment. Multimodal LLMs may support the process by proposing alternative organizational structures, identifying ambiguities in field definitions, suggesting opportunities for simplification, and assisting with annotation guidance and documentation, but final schema design decisions remain the responsibility of the human expert.

The output of this stage is a metadata schema comprising metadata fields, definitions, organizational structure, annotation guidance, examples, and other documentation required to support consistent metadata creation and downstream applications.

\section{Case study: Developing the Data Snapshot Metadata Schema}
\label{sec:case_study}

This section demonstrates the proposed methodology through one complete execution of the workflow for a class of multimodal analytical artifacts that lacked an established metadata schema. The resulting metadata schema is presented not as a definitive standard for this artifact type, but as evidence that the proposed methodology can produce a coherent, deployment-ready initial metadata schema where no suitable standard exists.

The case study describes the representative dataset, the execution of the proposed workflow, the implementation of each workflow stage, and the resulting metadata schema. The intermediate knowledge artifacts generated throughout execution also provide the empirical foundation for the analyses presented in the following section.

\subsection{Artifact type}

The case study focuses on \emph{data snapshots}: semantically meaningful analytical artifacts extracted from institutional PDF documents and managed as independent information objects. Data snapshots preserve their analytical meaning outside the context of their source documents and therefore require metadata describing the snapshot itself rather than only its source document.

Typical data snapshots include statistical tables, analytical charts, geospatial maps, monitoring dashboards, financial summaries, composite figures, and other visual analytical objects containing textual, numerical, and spatial information. Additional examples of data snapshots are provided in Appendix~\ref{appendix:datasnapshots}.

As discussed in our previous work, treating data snapshots as independent information objects enables downstream retrieval, indexing, comparison, and metadata extraction workflows that are difficult to support using document-level metadata alone. However, no existing metadata schema adequately captured the descriptive information required for this artifact type, making data snapshots an appropriate case study for evaluating a methodology designed to engineer an initial metadata schema for previously unsupported artifact types.

\subsection{Case study dataset}

\section{Analysis of semantic transformations}

The case study produced a sequence of explicit intermediate knowledge artifacts spanning metadata observations, metadata field profiles, candidate ontology, refined ontology, validation evidence, and the final metadata schema. Collectively, these artifacts document how a heterogeneous collection of representative data snapshots was progressively transformed into an operational metadata schema.

Rather than evaluating only the final metadata schema, this section examines the semantic transformation performed by each intermediate knowledge artifact. The objective is to understand how each intermediate representation contributes to the overall engineering process and why these intermediate artifacts provide a useful decomposition of metadata schema engineering. Across the five transformations, semantic complexity is progressively reduced while preserving the evidence required for the subsequent reasoning task.

The analysis is organized around five transformation-focused questions, each examining the contribution of one semantic transformation within the proposed methodology:

\begin{enumerate}
    \item How did independent metadata discovery characterize the semantic space?
    \item How did metadata field profile aggregation transform localized observations into reusable semantic evidence?
    \item How did conceptual abstraction transform semantic evidence into a coherent conceptual vocabulary?
    \item How did ontology validation strengthen confidence in the conceptual vocabulary?
    \item How did schema engineering transform a conceptual vocabulary into an operational metadata schema?
\end{enumerate}

\subsection{Independent semantic discovery}

The first stage of the methodology sought to characterize the semantic space of the target artifact type through independent metadata discovery. Each representative data snapshot was analyzed independently, allowing candidate metadata concepts to emerge without influence from previously processed data snapshots. This design intentionally prioritized semantic exploration before any vocabulary normalization or ontology engineering.

Consistent with the prompting objective of identifying 10--15 reusable metadata fields per artifact, each snapshot yielded approximately 14--15 candidate metadata fields. \subsection{Metadata field profiles as reusable semantic evidence}

Metadata discovery intentionally produces localized metadata observations describing individual artifacts, preserving semantic diversity but leaving ontology induction to reason over thousands of individual observations rather than the discovered vocabulary as a whole. To bridge this gap, the methodology introduces metadata field profiles, which aggregate observations sharing the same candidate metadata field into a single evidence-rich semantic representation.

Aggregating the 3,041 metadata observations resulted in 833 metadata field profiles, reducing the number of semantic units requiring subsequent analysis by approximately 73\% (Table~\ref{tab:aggregation_summary}). Importantly, aggregation did not perform any semantic abstraction. Aggregation simply combined repeated occurrences of identical candidate metadata fields while preserving the supporting evidence associated with each field, including representative observed values, descriptive summaries, explanatory reasoning, and occurrence statistics.

\begin{table}[!ht]
    \centering

The principal effect of aggregation was therefore not compression itself, but a change in the unit of semantic reasoning. During metadata discovery, each observation represents a localized interpretation of a single artifact. Metadata field profiles instead summarize the collective evidence associated with a candidate metadata field across the representative artifact collection. Ontology induction therefore reasons over evidence-rich semantic profiles rather than thousands of isolated metadata observations.

This change substantially enriches the semantic evidence available for conceptual abstraction. Individual metadata observations contain only localized evidence associated with a single artifact. In contrast, metadata field profiles accumulate representative values, descriptive summaries, explanatory rationale, occurrence statistics, and empirical support across many artifacts. Rather than comparing isolated field names, ontology induction can compare candidate metadata fields using their accumulated semantic characteristics.

Rather than producing a final ontology in a single step, this progressive abstraction strategy separated semantic consolidation from human ontology refinement (Table~\ref{tab:ontology_progression}).

Concepts were merged when maintaining separate metadata fields offered little practical benefit, reintroduced when operational requirements justified restoring previously abstracted distinctions, renamed to improve clarity and consistency, refined to broaden their applicability, or removed when their operational value did not justify additional annotation complexity.

Schema engineering also reintroduced concepts when operational requirements justified restoring distinctions that had previously been abstracted. For example, \texttt{panel\_title} was merged into \texttt{title} during ontology engineering because the distinction was not considered semantically significant at the conceptual level. During schema engineering, however, \texttt{panel\_title} was reinstated as an independent metadata field to support annotation and retrieval of multi-panel figures. The resulting schema therefore preserves the conceptual coverage established during ontology engineering while selectively modifying semantic distinctions according to operational requirements.

Finally, the resulting metadata fields were organized into nine semantic modules representing complementary aspects of data snapshot metadata. These modules improve schema readability, annotation guidance, and future extensibility while serving purely as an organizational structure rather than a hierarchical extension of the ontology.

Schema engineering completed the transition from a validated conceptual ontology to an operational metadata specification suitable for annotation and retrieval. The resulting metadata schema should therefore be viewed not as a direct encoding of the ontology, but as an operational specification that selectively preserves semantic distinctions according to their practical value for annotation, retrieval, and long-term maintenance.

Viewed collectively, the analysis of the five semantic transformations illustrates that metadata schema engineering is not a single inference task but a progressive knowledge engineering process. Each intermediate knowledge artifact reduces semantic complexity while preserving the evidence required for the next stage of reasoning, enabling semantic discovery, conceptual abstraction, ontology validation, and operational schema design to be performed as distinct but complementary activities. This separation allows multimodal LLMs and human experts to contribute complementary strengths throughout the engineering process while maintaining transparency and explicit human oversight.

\section{Discussion}

\subsection{Metadata schema engineering as an emerging knowledge engineering problem}

The methodology suggests that engineering an initial metadata schema for an emerging artifact type constitutes a distinct knowledge engineering problem that is not explicitly addressed by existing work on metadata standards, ontology engineering, or metadata extraction. Within the methodology, ontology engineering and metadata schema engineering are therefore treated as complementary rather than interchangeable activities: ontology engineering establishes a coherent conceptual vocabulary, whereas schema engineering transforms that vocabulary into an operational specification suitable for annotation and deployment.

Metadata standards provide mature descriptive vocabularies that have evolved through long-term community consensus but generally offer limited guidance on how an initial operational schema should be engineered before such a community exists. Conversely, metadata extraction assumes that an appropriate schema has already been defined and focuses on populating its fields from new artifacts. Between these activities lies an earlier engineering problem: discovering the metadata concepts required to describe a previously unsupported artifact type and organizing them into a practical metadata specification.

As illustrated by the case study, separating ontology engineering from schema engineering required additional design decisions concerning annotation practice, retrieval requirements, operational simplicity, and long-term maintainability that extended beyond conceptual modeling. For example, conceptually distinct ontology concepts were sometimes consolidated because maintaining separate metadata fields offered limited operational benefit, whereas other concepts were retained despite relatively low empirical support because they were considered important for annotation and retrieval.

More broadly, the methodology highlights a knowledge engineering problem that has not been explicitly treated as distinct from ontology engineering, metadata standardization, or metadata extraction: producing an initial metadata schema for emerging artifact types before mature standards or community conventions have developed. As new multimodal information objects continue to emerge, systematic methodologies for Version~1 metadata schema engineering are likely to play an increasingly important role alongside existing work on ontology engineering, metadata standardization, and metadata extraction.

By preserving explicit intermediate knowledge artifacts throughout the engineering process, the methodology also provides a transparent and auditable record of how the resulting metadata schema was developed. Rather than producing a metadata schema as a single opaque output, each design decision can be traced back through the candidate ontology, metadata field profiles, and original metadata observations that motivated it. This traceability supports review, revision, and future evolution of the metadata schema while preserving the evidence underlying every engineering decision.

\subsection{Human--LLM collaboration in metadata schema engineering}

The case study demonstrates that multimodal LLMs are most effective in metadata schema engineering not as autonomous schema designers, but as collaborators that support different forms of semantic reasoning throughout a structured engineering process. Rather than replacing expert judgment, the methodology deliberately assigns complementary responsibilities to multimodal LLMs and human experts.

Across the workflow, multimodal LLMs proved most valuable in tasks involving semantic exploration, evidence synthesis, and large-scale semantic comparison. These capabilities enabled rapid discovery of candidate metadata concepts, conservative abstraction into candidate ontologies, and ontology-constrained classification for validation, allowing human experts to reason over structured semantic evidence rather than isolated artifacts.

By contrast, the engineering decisions that ultimately determined the deployed metadata schema required reasoning beyond semantic similarity. Defining conceptual boundaries, distinguishing descriptive metadata from extraction outputs, balancing semantic granularity against annotation simplicity, and evaluating deployment trade-offs all depended on intended application and operational requirements rather than semantic relationships alone.

An additional practical observation from the case study is that the methodology enabled the complete schema engineering process to be carried out by a single researcher within a relatively short period of time. By using multimodal LLMs to accelerate semantic exploration, concept organization, and evidence synthesis, the methodology reduced the amount of manual synthesis required throughout the engineering process while preserving expert oversight over deployment decisions.

These observations suggest that the principal role of multimodal LLMs is to accelerate the exploratory and analytical stages of knowledge engineering while leaving conceptual and operational decisions to human experts. Rather than treating metadata schema engineering as a single prompting task, the methodology frames human--LLM collaboration as a structured reasoning process in which each participant contributes complementary forms of intelligence. This division of responsibility enables larger semantic search spaces to be explored efficiently while concentrating expert effort on the conceptual and operational decisions that most directly determine the quality of the deployed metadata schema.

\subsection{Broader implications and future directions}

The proposed methodology illustrates the value of decomposing complex human--AI knowledge engineering tasks into explicit intermediate knowledge artifacts connected through successive semantic transformations. Rather than treating LLM-assisted reasoning as a single opaque inference, the workflow externalizes semantic discovery, conceptual abstraction, validation, and schema design into independently reviewable stages. This decomposition improves transparency, supports iterative refinement, and preserves an explicit record of the reasoning behind schema design decisions. Similar principles may prove valuable for other human--AI knowledge engineering tasks, including taxonomy construction, ontology engineering, scientific knowledge organization, and related forms of structured conceptual modeling.

Although demonstrated through metadata schema engineering for data snapshots, the methodology was intentionally designed to be domain independent. The workflow depends not on any particular document collection or artifact type, but only on representative artifacts from which metadata concepts can be discovered together with sufficient domain expertise to guide ontology and schema engineering. Consequently, the methodology may be applicable to a broad range of emerging multimodal artifact types that lack mature descriptive standards, where the underlying challenge remains the same: discovering the metadata concepts needed to describe a previously unsupported class of artifacts before community conventions have emerged.

The methodology is likewise independent of any particular multimodal language model. Although the case study employed a contemporary multimodal LLM, the workflow relies only on general capabilities for semantic interpretation, abstraction, and structured reasoning. As future models improve, they may enhance individual workflow stages without requiring fundamental changes to the methodology. Likewise, as reporting practices, analytical conventions, and application requirements evolve, new representative artifacts can be incorporated into subsequent iterations to produce revised metadata observations, updated ontologies, and new schema versions while preserving the evidence underlying each design decision.

Future work should evaluate the methodology across substantially different artifact domains, compare it with traditional expert-only and alternative human--AI schema engineering approaches, and investigate collaborative workflows involving multiple domain experts. Additional decision-support techniques, such as similarity-based clustering, community detection, and interactive semantic visualization, may become increasingly valuable as ontology size and conceptual complexity grow.

As multimodal information objects continue to proliferate, the challenge is unlikely to be metadata extraction alone, but the systematic engineering of the metadata schemas that make extraction possible. Viewed in this broader context, the proposed methodology should be understood not simply as a procedure for producing a single metadata schema, but as a reusable knowledge engineering framework for systematically engineering, documenting, and evolving metadata schemas for emerging multimodal artifact types. By making intermediate knowledge artifacts explicit and assigning complementary responsibilities to multimodal LLMs and human experts, the methodology provides a practical framework for addressing this emerging knowledge engineering problem.

\section{Limitations}

Although the methodology is demonstrated through a complete case study, its generality, effectiveness, and scope remain subject to several limitations.

One limitation concerns empirical validation. The methodology was evaluated through the engineering of a metadata schema for data snapshots extracted from institutional documents. Although this artifact type encompasses diverse visualization formats, reporting styles, and document sources, the evidence presented in this paper is derived from a single application domain. Additional case studies involving substantially different multimodal artifact types would provide stronger evidence regarding the generality of the methodology. In addition, because metadata discovery begins from a representative artifact sample, the resulting schema is necessarily influenced by the coverage and representativeness of the artifacts selected for analysis.

Another limitation is that the methodology intentionally adopts a human-in-the-loop design. While multimodal LLMs supported metadata discovery, semantic abstraction, and large-scale classification, the conceptual and operational decisions that determined the final ontology and metadata schema remained expert-driven. Consequently, the quality of the resulting schema depends on the expertise of the human reviewers and their ability to make consistent conceptual and operational judgments. The methodology therefore should not be interpreted as a fully automated approach to metadata schema engineering, but rather as a structured framework for supporting expert knowledge engineering through AI-assisted semantic reasoning.

A further limitation is that this work focuses on demonstrating methodological feasibility rather than comparative evaluation. The case study does not compare the methodology with expert-only workflows, fully automated approaches, or alternative human--AI collaboration strategies. Future comparative studies would help clarify the relative advantages, trade-offs, scalability, and reproducibility of different approaches to metadata schema engineering.

Finally, the principal contribution of this paper is the methodology rather than the specific metadata schema produced by the case study. The Data Snapshot Metadata Schema should therefore be regarded as an initial operational schema that may continue to evolve as additional artifact types, application requirements, and community feedback become available. Successful application of the methodology in other domains will likewise depend on the availability of representative artifacts, appropriate multimodal LLM capabilities, and sustained domain expertise throughout the knowledge engineering process.

\section{Conclusion}

Engineering an initial metadata schema for a previously unsupported artifact type remains a challenging knowledge engineering task. Although mature metadata standards, ontology engineering methodologies, and metadata extraction techniques provide important foundations, comparatively little attention has been devoted to the earlier problem of constructing an operational metadata schema before established vocabularies or community conventions exist.

This paper presented a human-in-the-loop methodology that decomposes metadata schema engineering into a sequence of explicit semantic transformations across metadata discovery, metadata field profile aggregation, ontology induction, ontology engineering, ontology validation, and schema engineering. Rather than treating schema development as a single prompting task or a purely manual activity, the workflow combines the complementary strengths of multimodal LLMs and human experts through explicit intermediate knowledge artifacts that support transparency, reproducibility, and iterative refinement.

The methodology was demonstrated through the development of the Data Snapshot Metadata Schema, an operational metadata schema for semantically meaningful analytical artifacts extracted from institutional documents. Beyond producing an operational metadata schema, the case study showed how heterogeneous metadata observations could be progressively transformed into a coherent conceptual ontology and ultimately into an operational metadata specification. It further demonstrated that multimodal LLMs were most effective in semantic discovery and abstraction, while ontology engineering, conceptual boundary setting, and operational schema design remained expert-driven.

More broadly, this work positions metadata schema engineering as a distinct knowledge engineering problem situated between ontology engineering, metadata standardization, and metadata extraction. As multimodal information objects continue to emerge across scientific, technical, and institutional domains, systematic methodologies for engineering, documenting, and evolving metadata schemas will become increasingly important. We hope this methodology provides a practical foundation for future research on transparent, human-centered approaches to AI-assisted knowledge engineering.

\subsection{Prompt design rationale}

The metadata discovery prompt was designed to elicit reusable metadata concepts rather than perform metadata extraction. Instead of populating a predefined schema, the model was instructed to behave as a metadata architect responsible for proposing candidate metadata fields that could contribute to a future metadata schema.

Several design principles were incorporated into the prompt. First, the model was instructed to distinguish reusable metadata concepts from snapshot-specific values, encouraging abstraction toward canonical metadata fields rather than enumerating observed categories or numerical values. Second, the prompt explicitly distinguished information available from document metadata from information that must be obtained from the snapshot itself, thereby emphasizing metadata that enriches document-level description. Third, the model was instructed to prioritize metadata concepts supporting retrieval, cataloging, provenance, and analytical reuse while de-emphasizing visual formatting and implementation-specific metadata. Finally, hallucination prevention guidelines required observed values to remain grounded in either the snapshot image or the accompanying document metadata, with uncertain values explicitly marked as not identifiable rather than inferred without evidence.

The resulting metadata observations therefore constitute reusable semantic hypotheses about candidate metadata fields rather than extracted metadata records.

\section{Appendix: Data Snapshot Metadata Schema}
\label{appendix:schema}

\begin{lstlisting}
# Data Snapshot Metadata Schema v1.1

## Overview

The Data Snapshot Metadata Schema v1.1 defines a standardized set of metadata fields for describing **data snapshots**--self-contained visual data artifacts extracted from institutional documents, including tables, charts, maps, dashboards, and composite figures.

The schema is intended to support:

- metadata extraction
- indexing and search
- retrieval
- downstream analytics

The schema is intentionally domain-agnostic and is designed to generalize across institutional documents from multiple organizations and subject areas.

The schema was developed through an iterative, human-in-the-loop process combining multimodal large language models, ontology induction, expert review, and quantitative validation.

---

# Scope

The schema describes metadata **about a data snapshot**.

It intentionally excludes:

- extracted numerical values
- OCR text
- table cell contents
- chart data reconstruction
- other extraction outputs

Metadata should only be populated when explicitly supported by the snapshot or its accompanying document context.

Metadata extractors **must not infer or hallucinate** values that are not evidenced by the source.

---

# Applicability

Each metadata field is optional.

Metadata should only be populated when explicitly supported by evidence contained within:

- the snapshot itself; or
- the accompanying source document, where explicitly permitted.

The absence of a metadata field should be represented as null rather than inferred.

---

# Schema Modules

## Identity & Discovery

### title

**Definition**

The primary title, caption, or heading that identifies the data snapshot.

**Examples**

# Metadata Extraction Guidelines

Metadata extractors should follow these principles:

1. Populate metadata only when supported by explicit evidence.

2. Do not infer, hallucinate, or fabricate metadata.

3. Prefer semantic meaning over literal wording.

4. Multiple values may be assigned where appropriate (for example, multiple geographic entities).

5. Preserve original terminology whenever practical.

6. Record missing metadata as null rather than inferred values.

7. The schema describes the snapshot-not the parent document as a whole.

8. Numerical values, OCR text, and reconstructed table contents belong to extraction outputs and are outside the scope of this metadata schema.
