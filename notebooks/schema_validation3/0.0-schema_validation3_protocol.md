# Data Snapshot Metadata Schema Validation 3 Protocol

**Status:** Approved for implementation

**Baseline:** Data Snapshot Metadata Schema v1.2

**Relationship to Validation 2:** Confirmatory coverage and representational-stability assessment using the same 202 snapshots

## 1. Research question

For each data snapshot:

> Given Data Snapshot Metadata Schema v1.2, this snapshot, and its
> parent-document context, is there any critical or possibly critical reusable
> metadata information about the snapshot that the schema cannot adequately
> represent without material semantic or relational loss, and whose omission
> or inadequate representation would materially impair interpretability,
> discoverability, or both?

At the study level, Validation 3 asks whether the implemented v1.2 schema
adequately covers the same 202 snapshots assessed in Validation 2 or whether
the revised concepts, nested structures, cardinalities, normalization
facilities, constraints, or definitions leave a material gap.

Validation 3 assesses v1.2 on its own. It does not run a paired v1.1.1
comparison and cannot attribute an outcome to the change from Markdown to
Pydantic. Both the schema design and its representation changed between
versions.

## 2. Validation design

Validation 3 is a confirmatory screen rather than a new metadata-discovery
exercise.

- Schema v1.2 is frozen after calibration and during the substantive run.
- The model assesses one snapshot per request.
- The complete generated JSON Schema, snapshot image, and parent-document
  metadata are supplied together.
- The model returns only critical or possibly critical gaps.
- The model does not inventory covered metadata, extract a complete metadata
  record, or design a replacement schema.
- Human adjudication determines whether a surfaced candidate warrants any
  schema change.
- No candidate changes the schema automatically.

The evaluated schema is generated at run start from the canonical Pydantic
`DataSnapshotMetadata` model. The checked-in JSON Schema and Markdown reference
are review and interoperability artifacts, not runtime inputs.

The model sees the generated JSON Schema rather than the Python validator
source. Validation 3 therefore assesses the representational capabilities,
exported constraints, and model-facing definitions expressed by that schema.
It is not a test of Python-only normalization or validator implementation.

## 3. Sample reuse and reproducibility

### 3.1 Substantive corpus

The substantive run reuses the 202 snapshots in
`notebooks/schema_validation1/data/snapshots`, with parent-document context
from `notebooks/schema_validation1/data/metadata`.

- The runner discovers every PNG in the existing source/type directory
  structure and processes files in sorted path order.
- The 202 filenames must exactly match the successful Validation 2 filenames.
- Each output record retains its snapshot filename, source corpus, artifact
  type, metadata filename, model, request settings, token usage, elapsed time,
  raw response, and parsed result.
- Successful snapshot filenames already present in the selected result JSONL
  are skipped on rerun. Errors remain eligible for retry.

These snapshots were held out from the original schema-discovery sample, but
they are not independent held-out evidence for v1.2 because v1.2 design was
informed by Validation 2 findings. Validation 3 therefore treats them as a
reused regression and representational-stability corpus.

### 3.2 Calibration samples

Calibration0 reuses the balanced twelve-snapshot calibration set from
Validation 1. It contains figures and tables from all three source corpora and
includes `document_699863_table_004.png`, which supplies the complete-schema
baseline for the provenance sensitivity control.

Later calibration rounds may use additional samples when the observed results
justify a new control or prompt adjustment. Each added round must document:

- why the round is necessary;
- how its samples were selected;
- whether each sample is reused or newly added;
- the expected sensitivity signal, if it is a control; and
- why its results are excluded from the substantive analysis.

New calibration samples do not expand or replace the 202-snapshot substantive
corpus. Permission is required before ignored or untracked local sample files
are added, copied, modified, or removed.

## 4. Evidence and metadata boundaries

### 4.1 Snapshot boundary

The snapshot is the object being described. Parent-document metadata may
clarify its subject, meaning, provenance, or relationship to its source
document.

A candidate gap must describe:

- the snapshot itself;
- the data represented in it; or
- provenance explicitly attached to it.

Information describing only the parent document is not a snapshot-schema gap.
Each candidate must identify its evidence and explain why the information is
metadata about the snapshot rather than document administration.

### 4.2 Reusable metadata boundary

The following remain outside the schema scope:

- numerical observations and extracted values;
- OCR output and reconstructed content;
- table cells, statistical estimates, and model results;
- snapshot-specific values proposed as schema concepts;
- visual styling without descriptive significance;
- extraction-pipeline artifacts; and
- unsupported inference or external knowledge.

An explicitly displayed methodological, uncertainty, or provenance statement
may be reusable metadata even when it contains a number.

## 5. Adequate representation

Schema v1.2 is adequate when its existing concepts and structures can preserve
the evidenced information without materially distorting its meaning or losing
a relationship needed for interpretation or discovery.

For each candidate, the model compares:

1. a faithful description of the evidenced metadata and the relationship that
   must be preserved; and
2. the best representation permitted by the closest existing v1.2 paths.

Closest paths use exact dot notation derived from the generated JSON Schema,
with `[]` marking array items, such as `variables[].unit` or
`dimensions[].category_groups[].categories`. A synonym, naming preference, or
alternative serialization style is not a gap when the existing schema can
preserve the same information faithfully.

A candidate may concern an absent concept, an inadequate relationship or
nesting structure, cardinality, normalization facility, exported constraint,
or definition. The model does not classify the candidate into one of these
categories; that classification belongs to human review.

## 6. Critical and possible gaps

A **critical** gap requires all of the following:

1. explicit evidence in the supplied inputs;
2. reusable snapshot metadata within the schema scope;
3. no adequate representation using existing v1.2 paths; and
4. a concrete material impact on interpretability, discoverability, or both.

A **possible** gap must still be plausible reusable snapshot metadata with a
plausible material impact, but uncertainty remains about the evidence,
existing-schema coverage, or materiality.

Information that is merely useful, convenient, specialized, desirable, or an
additional search facet is not reported. The model must not assume a particular
application, interface, user group, search behavior, or workflow.

## 7. Structured output

Each snapshot returns:

- `coverage_assessment`: `no_critical_gap_found`, `critical_gap_found`, or
  `possible_gap`; and
- `critical_or_possible_gaps`: an array containing only candidate gaps.

There is no snapshot-level rationale. `no_critical_gap_found` and an empty
candidate array are sufficient when no information meets the reporting
threshold.

Each candidate contains:

- a `gap_id` unique within the snapshot;
- `gap_status`: `critical` or `possible`;
- the missing or inadequately represented metadata;
- concise evidence from the supplied inputs;
- a faithful representation of the evidenced metadata and relevant
  relationship;
- why the information is snapshot metadata;
- exact closest v1.2 schema paths, or an empty list when none applies;
- why those paths may be inadequate;
- material impact: `interpretability`, `discoverability`, or `both`;
- the concrete material consequence; and
- an uncertainty note or null.

The response does not require a proposed field name because a v1.2 gap may be
structural rather than a missing field. It does not ask the model to recommend
accepting, rejecting, or implementing a change.

## 8. Known v1.2 representation status

### 8.1 Category-group hierarchy

Validation 2 surfaced a nested table-column hierarchy problem. Schema v1.2
addresses that case through `dimensions[].category_groups`, which associates
one level of explicit category groups and their categories with a dimension.

Validation 3 treats this as an implemented representation. A hierarchy-related
candidate must explain why the existing structure is materially inadequate for
the evidenced case rather than merely observe that the table contains grouped
headers.

### 8.2 Panel-specific metadata associations

Schema v1.2 retains ordered `panel_titles` and snapshot-level metadata. It does
not encode panel-specific associations among titles, visualization types,
subjects, variables, or time periods. This is a known limitation recorded for
later decision with Aivin.

If the model surfaces this limitation, human review records it as a known
pending design issue rather than a newly introduced regression. Validation 3
may provide additional evidence relevant to that decision, but it does not
resolve the panel model automatically.

## 9. Calibration

### 9.1 Calibration0: complete-schema baseline

Calibration0 evaluates the complete v1.2 schema against the twelve existing
calibration snapshots. Review checks:

- adherence to the critical/possible threshold;
- exclusion of broad metadata inventories and extraction content;
- exclusion of document-only administration;
- use of exact, valid v1.2 schema paths;
- attention to structural and relational adequacy rather than field names
  alone;
- concise, evidence-backed candidate explanations;
- internally consistent structured outputs; and
- response length, latency, cache use, and cost.

Calibration does not systematically audit `no_critical_gap_found` cases for
false negatives.

### 9.2 Calibration1: provenance sensitivity control

Calibration1 uses `document_699863_table_004.png`. Its footer explicitly states
that the data are from CIDTc, that they apply to 1987/88, and that further
discussion of data construction appears in the text.

The complete-schema assessment from Calibration0 is the paired baseline. The
control changes only the model-facing schema copy by removing the top-level
`provenance` and `interpretive_notes` properties and neutralizing remaining
references that would disclose those removed paths. The canonical Pydantic
model and checked-in generated artifacts are not modified.

The required sensitivity signal is at least one critical or possible candidate
identifying the absent data-source or provenance capability supported by “Data
are from CIDTc.” The represented date remains covered by
`temporal_coverage.period` and is not an expected gap. A result that does not
surface the provenance concept requires review before the substantive run.

Calibration1 is a methodological control. Its output is excluded from
substantive candidate counts and schema conclusions.

### 9.3 Adaptive calibration

Calibration0 and Calibration1 are reviewed before the instrument is frozen.
Unexpected suppression, over-generation, invalid paths, boundary violations,
or ambiguous sensitivity results may justify another numbered calibration
round, including one with newly selected samples.

Each prompt, schema presentation, or configuration change restarts the relevant
baseline check. Calibration ends only after the instrument and its remaining
limitations are documented. No full-run request is made before explicit
approval after calibration review.

## 10. Execution pattern

Validation 3 mirrors Validation 2:

- GPT-5.5 with medium reasoning;
- Flex service tier;
- prompt caching;
- an 8,000-token output ceiling;
- Pydantic Structured Outputs;
- one snapshot per request;
- progress reporting with `tqdm`;
- resumable successful-result JSONL;
- a separate error JSONL;
- no automatic retry policy;
- retry by rerunning the notebook;
- retained raw response, parsed output, request settings, token usage, and
  elapsed time; and
- separate outputs for each calibration/control round and the full run.

The model and request settings remain configuration-driven. The user executes
every live API cell. The tracked schema implementation, prompts, configuration,
notebook, and Git revision, together with the filenames and request settings in
the output records, provide the reproducibility record. Validation 3 does not
add a separate preparation step, run fingerprint, run manifest, or `run.json`.

## 11. Programmatic quality controls

Before API execution, the runner verifies:

- a non-empty generated v1.2 schema and nested path inventory;
- a valid model configuration;
- at least one PNG in the source/type directory structure;
- matching source/type filename structure;
- resolvable parent-document metadata; and
- distinct results and error paths.

The notebook preflight verifies that Calibration0 resolves exactly twelve
snapshots and that the substantive input filenames exactly match all 202
successful Validation 2 filenames.

After parsing, the runner verifies:

- unique gap identifiers within a snapshot;
- exact closest paths from the generated schema path inventory;
- consistency between the coverage status and candidate contents; and
- resumability by successful snapshot filename.

The provenance ablation is tested against a local schema copy to ensure it
cannot mutate the cached canonical schema or generated review artifacts.

## 12. Human adjudication

Human review examines every critical candidate, every possible candidate, and
technical failure requiring rerun. It does not audit model-assessed no-gap
cases.

For each surfaced candidate, the reviewer determines whether it is:

- adequately represented by an existing v1.2 path;
- not reusable snapshot metadata;
- parent-document metadata;
- extraction content;
- insufficiently evidenced or insufficiently material;
- a known panel-association limitation;
- a documentation, normalization, constraint, cardinality, or structural
  concern; or
- a meaningful missing metadata concept.

The reviewer may additionally consider scope relevance, reusability, semantic
fidelity, generalizability, parsimony, consistency, granularity, clarity, and
maintainability. Candidate frequency is supporting evidence, not an acceptance
rule.

## 13. Analysis and claim boundary

The final analysis reports:

- successful and failed calls;
- model-assessed coverage status by corpus and artifact type;
- critical and possible candidate counts;
- impact categories and closest schema paths;
- recurring candidate concepts and evidence;
- known limitations resurfaced; and
- human-adjudication outcomes.

Calibration and sensitivity-control outputs are reported separately and are
excluded from substantive counts.

Because no-gap assessments are not independently audited, Validation 3 does not
estimate model recall or a false-negative rate. Because the 202 snapshots
informed v1.2 design and there is no paired version comparison, it does not
establish an independent replication or a causal Markdown-versus-Pydantic
effect.

If no surfaced candidate warrants changing v1.2 after human review, the
supported conclusion is:

> Within the reused 202-snapshot regression corpus and the intended schema
> scope, Validation 3 surfaced no critical or possibly critical candidate that
> required changing Data Snapshot Metadata Schema v1.2. The known limitation
> concerning panel-specific metadata associations remains pending separately.

If human review accepts a candidate, the report states the evidenced v1.2
limitation and its scope. It does not infer that Pydantic caused the limitation
or that v1.1.1 represented the information adequately without a separate
comparison.
