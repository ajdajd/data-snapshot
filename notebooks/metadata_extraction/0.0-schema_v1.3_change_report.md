# Data Snapshot Metadata Schema v1.3 Change Report

**Date:** September 11, 2026
**Status:** Planning and incremental implementation
**Baseline:** Frozen Data Snapshot Metadata Schema v1.2
**Working version:** Data Snapshot Metadata Schema v1.3

## Executive summary

This report tracks the proposed changes arising from the final human QA of
Schema v1.2. The proposed changes are substantial enough to publish as Schema
v1.3. Versioning the result separately preserves the historical interpretation
of Schema Validation 3: that exercise evaluated Schema v1.2 before the
post-validation multi-axis amendment. It did not evaluate the proposed v1.3
semantics, examples, field types, or documentation.

The working principle for this review is:

> Schema v1.3 should preserve the semantic content of Schema v1.1.1, with
> differences limited to approved normalization, standardization, renamed
> fields, and nested relationships.

The review addresses one change at a time. Each decision records its
relationship to the completed Schema Validation 3 conclusion and its expected
effect on metadata extraction before implementation. Approved decisions are
implemented in coherent bundles while their rationale is current. No Schema
Validation 4 or v1.3 rerun is planned. The original Schema Validation 3 results
and report remain attached to the frozen v1.2 instrument.

The next empirical stage is metadata extraction with a newly developed
pipeline. That work will be planned in a separate thread after the v1.3 schema
decisions are complete. This report records extraction implications but does
not design the new pipeline.

## Recommended review sequence

The items should be decided individually, but not strictly in numerical order.
The following order minimizes rework:

1. Establish the cross-cutting representation rules: items 10, 1, and 11.
2. Resolve nested relationships and cardinality: items 8 and 9.
3. Resolve field-specific normalization behavior: items 2, 3, 4, 5, 7,
   and 13.
4. Resolve the location-type semantic boundary separately: item 15.
5. Reconcile the generated and supporting documentation: items 6 and 12.

For each item, the review should produce a short decision record containing:

- the v1.1.1 semantic requirement;
- the current v1.2 representation;
- the proposed v1.3 representation;
- standards or vocabulary evidence, when applicable;
- relationship to the completed Schema Validation 3 result;
- expected effect on metadata extraction;
- the accepted decision and rejected alternatives; and
- the implementation and verification scope.

## 1. Simplify fields without a normalization vocabulary

**Status:** Implemented and verified with items 10 and 11.

Schema v1.2 uses generic `ControlledTerm` in 12 field paths. The proposed rule
is to use plain semantic text when the application has not selected a
vocabulary and has no need to preserve a code or concept URI. The existence of
a broad standards property or ontology is insufficient by itself. A structured
term remains justified when the field may carry a meaningful dataset-specific
code or when a concrete, maintained external vocabulary fits the field's v1.1.1
semantics.

This rule depends on two limited cross-cutting proposals from items 10 and 11:

- `source_text` means literal source-visible wording that itself denotes the
  represented term. It is not a visual clue, contextual evidence, inferred
  classification, paraphrase, or normalized label. A plain-text field instead
  records the schema-level semantic answer and may be directly stated or
  directly supported by visible content.
- The universal five-property `ControlledTerm` should be replaced by the
  smallest value shape justified by each field: plain text, a normalized term
  with a closed local value, or a coded term with optional exact vocabulary
  identifiers. The complete review of the specialized normalized models remains
  under item 11.

### Field proposals

| Current field path | Proposed v1.3 representation | Rationale | Potential impact on Schema Validation | Impact on Metadata Extraction |
|---|---|---|---|---|

Dublin Core, Schema.org, and SDMX provide ways to represent subjects or subject schemes, but the application has not selected a domain vocabulary that covers the intended corpus. | The subject concept remains covered. The simpler value may reduce representation concerns caused by unexplained normalization properties, but the direction and size are unknown. | The extractor can return `Agriculture` when that domain is supported by visible content even if the word does not appear. It no longer has to invent `source_text` or an unofficial normalized value. |
| `population_group` | `NonEmptyText` | DDI represents a population through textual description and references to a structured Universe; it does not supply one general list containing values such as refugees, children under five, and host communities. | The population concept remains covered, with a representation closer to v1.1.1. | Produces one semantic population description without unsupported term metadata. |

IATI sector, aid-type, and transaction classifications describe narrower dimensions and do not form one equivalent vocabulary. | The intervention concept remains covered. The proposed coded-term model would retain `source_text`, `code`, `scheme`, and
`uri` only. It would omit the current open-ended `normalized_value`; a code or
URI already identifies the vocabulary concept, and its preferred label can be
resolved from the named scheme. Whether `source_text` or a code must be present
is deferred to item 11 together with enrichment and requiredness rules.

Relevant standards evidence includes the [DDI PopulationType model](https://docs.ddialliance.org/DDI-Lifecycle/3.3/model/composite-types/PopulationType/),
[DDI Mode Of Collection vocabulary](https://rdf-vocabulary.ddialliance.org/ddi-cv/ModeOfCollection/4.0.3/ModeOfCollection.html),
[DDI Type of Instrument vocabulary](https://rdf-vocabulary.ddialliance.org/ddi-cv/TypeOfInstrument/1.1.2/TypeOfInstrument.html),
[DDI Contributor Role vocabulary](https://rdf-vocabulary.ddialliance.org/ddi-cv/ContributorRole/1.0.2/ContributorRole.html),
[IATI Finance Type contract](https://reference.iatistandard.org/en/iati-standard/203/activity-standard/iati-activities/iati-activity/transaction/finance-type/),
[IATI Location Type list](https://reference.iatistandard.org/en/iati-standard/203/codelists/locationtype/),
[SDMX codelist model](https://docs.sdmx.org/en/i1-doc/Sections/Section1/SDMX_2-1_SECTION_1_Framework.html),
[SKOS concept and notation model](https://www.w3.org/TR/skos-reference/), and
[DCAT qualified-role guidance](https://www.w3.org/TR/vocab-dcat-3/#Property:relationship_had_role).

**Schema Validation impact.** These proposals do not alter the conclusion that
no new standalone metadata field was needed. They change the representation of
accepted concepts and may help explain why some v1.2 structures appeared more
elaborate than their underlying semantics required. No rerun is planned.

**Metadata Extraction impact.** Six semantic field groups become plain text.
Five groups retain structured coding because they have a concrete coding use.
This reduces unsupported normalization while preserving exact external or
dataset-specific identifiers where they are meaningful.

## 2. Show normalization through complete worked examples

**Status:** Approved direction; complete field inventory pending.

Preserve every original v1.1.1 example expression. For fields with a genuine
normalization structure, add normalized properties only when the mapping is
deterministic. Retain source-only examples when a correct mapping depends on
missing context.

The audit must cover temporal expressions and granularity, places and
geographic levels, languages, currencies, units, statistical forms, and every
other retained normalized type. Examples at the root field and referenced-type
levels must not contradict each other.

**Schema Validation impact.** Validation 3 supplied the complete v1.2 JSON
Schema, including its then-current examples, as model context. The revised
examples belong to v1.3 and do not retroactively change the completed results.
They document one reason the v1.2 and v1.3 model-facing instruments differ.

**Metadata Extraction impact.** Complete examples should teach the extractor
which properties belong together and when normalization is safe. They must not
suggest that optional normalized properties are mandatory or that ambiguous
values should be guessed.

## 3. Correct visualization examples and semantics

**Status:** Approved direction; coordinated examples pending.

Use `normalized_value` when the type is inferred directly from visible form.
Use `source_text` only for wording that explicitly names the visualization
form. For example:

```json
{"normalized_value": "bar_chart"}
```

If the snapshot title contains “Respondent Demographic Bar Graph,” a paired
value may be:

```json
{
  "source_text": "Bar Graph",
  "normalized_value": "bar_chart"
}
```

**Schema Validation impact.** This clarifies the intended use of an existing
field. It does not add a concept or change the completed Validation 3
adjudication.

**Metadata Extraction impact.** The extractor can classify visible form without
fabricating source wording. Explicit labels remain available for traceability.

## 4. Define the visualization null fallback

**Status:** Direction approved; unfamiliar explicit labels require a decision.

The proposed instruction is: “If no listed visualization type is clearly
supported, return `null`; do not force a match to the closest vocabulary
value.” This conflicts with the current normalization rule that permits an
explicitly named unfamiliar visualization type as a source-only term.

One possible resolution is:

- emit a listed `normalized_value` when visual evidence clearly supports it;
- preserve an explicitly written unfamiliar type in `source_text` without a
  normalized value; and
- return `null` when neither condition is satisfied.

**Schema Validation impact.** The choice determines how v1.3 describes the
coverage of unfamiliar types. It remains a representation decision within the
existing visualization concept and does not reopen the completed field-inventory
conclusion.

**Metadata Extraction impact.** The rule controls forced enum matches and
whether unfamiliar explicit labels are preserved for later vocabulary review.

## 5. Clarify identifier evidence and enrichment boundaries

**Status:** Approved direction; exact wording pending.

Identifier values may come from the snapshot or trusted metadata. Schemes,
issuers, and URIs may also come from configured or verified enrichment. The LLM
extractor must not infer or manufacture these values from model knowledge or
from the apparent shape of an identifier.

**Schema Validation impact.** This is an evidence-boundary clarification within
existing identifier structures. It does not alter the completed conclusion.

**Metadata Extraction impact.** The extractor needs explicit precedence and
provenance rules for snapshot evidence, trusted metadata, configured mappings,
and later verified enrichment.

## 6. Reorganize the generated Markdown reference

**Status:** Approved design; implementation pending.

Keep the validation and serialization section. Organize the Snapshot fields
tables and field-definition subsections by the v1.2/v1.3 modules. Place all
nested models and enums under one `Referenced types` section, with each type one
heading level below it.

**Schema Validation impact.** None. The Markdown is a human review artifact;
Validation 3 used its frozen generated JSON Schema instrument.

**Metadata Extraction impact.** The change improves human implementation and
review. It has no direct model effect unless a future extractor is explicitly
given the Markdown reference.

## 7. Replace `country_code` with `iso3_code`

**Status:** Approved direction; edge cases and exact name pending.

Use the ISO 3166-1 alpha-3 country code, such as `PHL`, instead of the current
alpha-2 value `PH`. The field must exclude World Bank three-character region or
aggregate codes that are not ISO country codes. ISO 3166-2 subdivision codes
continue to use an alpha-2 country prefix.

**Schema Validation impact.** The geographic concept remains present. This is a
normalization change and does not alter the Validation 3 field-inventory
conclusion.

**Metadata Extraction impact.** The extractor and normalizer must map exact
country identities to alpha-3 values and leave the field absent when the
mapping is ambiguous or inapplicable. Region names remain names or use an
appropriate region identifier such as UN M49.

## 8. Review nested requiredness against legacy representability

**Status:** Decision required.

The current model rejects several partial representations that v1.1.1 could
express independently:

- a unit, currency, or statistical form without `Variable.name`;
- categories or presentation roles without `Dimension.name`;
- an attribution without an explicit role; and
- a geographic role or location type without a named or source-visible
  location.

The review must decide whether these are necessary relationship constraints or
unintended losses of legacy semantic content. The schema should not force the
extractor to invent a parent value merely to retain a visible child value.

**Schema Validation impact.** This may identify restrictions in how accepted
concepts are nested, similar in kind to a representation concern rather than a
missing-field finding. Resolving those restrictions does not require a new
standalone metadata concept.

**Metadata Extraction impact.** This determines whether the extractor should
omit visible metadata, infer a parent, or emit a partially populated nested
object. The accepted choice must be explicit.

## 9. Define handling of shared measurement qualifiers

**Status:** Decision required.

The variable-centric structure does not yet state what to do when one unit,
currency, multiplier, or statistical form visibly applies to several
variables. The likely representation is to repeat the qualifier on each
applicable variable, but this should be decided and documented rather than left
to extractor behavior.

**Schema Validation impact.** This documents how existing variable and
qualifier concepts relate. It does not add a field or revise the completed
conclusion.

**Metadata Extraction impact.** The decision controls repetition and attachment
across variables and prevents a shared label from being attached to only one
variable arbitrarily.

## 10. Apply one `source_text` rule throughout the schema

**Status:** Implemented and verified with items 1 and 11.

Retain the name `source_text` and define it consistently as:

> Exact text or symbol visible in the snapshot that explicitly expresses the
> value represented by this object. Omit it when the value is inferred from
> visual form, structure, or context rather than transcribed.

The rule applies as follows:

| Value type | `source_text` use | Value when no explicit source expression exists |
|---|---|---|
| Plain semantic text approved under item 1 | Not applicable; the field stores the semantic answer directly. | Return the directly supported semantic answer, such as `Agriculture`, without pretending it was transcribed. |
| Statistical form | Preserve an explicit word or symbol such as `Average` or `%`. | Use only the closed `normalized_value` when the form is directly supported but not explicitly named. |
| Visualization type | Preserve explicit wording such as `Bar Graph`. | Use only the closed `normalized_value` when the form is inferred from the visual design. |
| Temporal granularity | Preserve explicit wording such as `Annual`. | Use only the closed `normalized_value` when the granularity is supported by the time sequence or structure. |
| Geographic level | Preserve explicit wording such as `Province`. | Use only the closed `normalized_value` when the level is supported by the snapshot but not explicitly named. Do not use unsupported model-world knowledge. |
| Language | Preserve a language label only when it is itself displayed, such as a language selector reading `English`. | Use the BCP 47 `tag` when the language is identified from the displayed content. |
| Place | Preserve the displayed place expression, such as `The Philippines`. | Use the preferred `name` and applicable codes when the place is directly supported visually or by trusted metadata but not textually named. |
| Unit and currency | Preserve the displayed word, abbreviation, or symbol, such as `%`, `USD`, or `$`. | Do not infer a unit or currency from an unlabeled numeric scale. Add a normalized code only when the visible expression and context support it. |
| Temporal expression | Preserve a complete displayed expression, such as `2015–2020`. | Permit normalized `start`, `end`, `relation`, and `precision` without synthesizing a `source_text` string from separate axis labels. |

The temporal-expression case requires changing `TemporalExpression.source_text`
from required to optional and requiring at least one of `source_text`, `start`,
or `end`. Otherwise an extractor would have to manufacture `2015–2020` when the
snapshot only shows separate yearly axis labels. Exact consistency checks among
`relation`, bounds, and precision remain applicable.

**Schema Validation impact.** This clarifies the evidence semantics of existing
fields. It may help explain model behavior under the v1.2 instrument but does
not change the adjudicated result.

**Metadata Extraction impact.** This is a foundational output rule. It prevents
the extractor from writing paraphrases or inferred category names into a field
presented as source evidence.

## 11. Review properties inherited by specialized term models

**Status:** Implemented and verified with items 1 and 10.

Remove the universal `ControlledTerm`. Replace it with two explicit structural
patterns in addition to the plain text fields approved in item 1:

| Pattern | Properties | Uses |
|---|---|---|
| Purpose-specific normalized term | `source_text`, closed-enum `normalized_value` | `StatisticalFormTerm`, `VisualizationTypeTerm`, `TemporalGranularityTerm`, and `GeographicLevelTerm` |
| Shared coded term | `source_text`, `code`, `scheme`, `uri` | Dimension categories, attribution roles, location types, financing instruments, and data-collection methods |

The four normalized term models should no longer inherit `code`, `scheme`, or
`uri`. Their local enum is the canonical normalized value. If an external
standard provides an equivalent code, the mapping belongs in schema-level
standards metadata or a maintained crosswalk rather than being repeated in
every extracted record.

The shared coded term should not contain `normalized_value`. Its validation
rules should be:

- at least one of `source_text`, `code`, or `uri` must be populated;
- `code` and `scheme` must be populated together; and
- `uri` must be an authoritative URI for the represented concept.

Each purpose-specific normalized term should require at least one of
`source_text` or `normalized_value`. This permits normalized-only inference,
paired source and normalized values, and source-only unfamiliar explicit terms
without accepting arbitrary strings as normalized values.

The implementation should use four small purpose-specific Pydantic models
rather than a public generic base that exposes unrelated properties. Shared
validation may remain an internal helper if it reduces duplication without
changing the generated public schema.

**Schema Validation impact.** This changes the breadth of normalization
properties within accepted concepts. It does not imply that Validation 3 missed
a new metadata field.

**Metadata Extraction impact.** Purpose-specific objects reduce output size and
discourage unsupported codes, schemes, and URIs.

## 12. Reconcile supporting documentation

**Status:** Pending final design decisions.

Known inconsistencies include:

- `normalized_label` in the normalization profile versus `normalized_value` in
  Pydantic;
- alpha-2 country guidance versus the proposed alpha-3 field;
- controlled-term guidance for fields proposed to become plain text; and
- source-only unfamiliar visualization guidance versus an unconditional null
  fallback.

The concept design, normalization profile, Python README, generated Markdown,
and generated JSON Schema must describe one final v1.3 contract. Historical
Schema Validation 3 materials must remain unchanged except for later contextual
notes that clearly distinguish the evaluated v1.2 schema from v1.3.

**Schema Validation impact.** Historical instrument files remain frozen. The
updated documentation will identify v1.3 as a later schema contract rather than
rewriting the meaning of the completed v1.2 study.

**Metadata Extraction impact.** Consistent documentation is necessary for
prompt design, normalization, implementation, and human review.

## 13. Align standards claims with actual validation strength

**Status:** Decision required.

The current implementation generally checks the syntax and casing of BCP 47,
ISO-like, M49, currency, and unit values without proving registry membership.
The documentation should either state this boundary precisely or a later
offline normalizer should validate values against a documented, pinned release.

**Schema Validation impact.** This does not add a metadata concept or change the
completed conclusion. It changes how confidently v1.3 can claim that normalized
values conform to an external standard.

**Metadata Extraction impact.** The choice determines whether a plausible but
nonexistent code passes initial extraction, fails validation, or is deferred to
verified enrichment.

## 14. Add semantic representability regression tests

**Status:** Skipped by decision.

Current tests confirm that legacy descriptions and example strings survive at
their v1.2 destinations. They do not establish that every retained v1.1.1
concept can be represented when related legacy fields are absent. A dedicated
35-concept representability matrix will not be added. Focused regression tests
will still accompany implemented behavior changes as routine verification.

**Schema Validation impact.** Skipping the dedicated matrix does not affect
model behavior or the completed results.

**Metadata Extraction impact.** There is no direct extraction effect. Focused
tests still protect each implemented behavior change.

## 15. Resolve the `location_type` physical-versus-administrative inconsistency

**Status:** Implemented and verified.

The v1.1.1 `location_type` definition and the v1.2 exported field description
say “The type of physical location represented,” but both use `District` as an
example. A district is an administrative unit. The v1.2 `GeographicLocation`
class docstring instead says “Physical or administrative location type,” so the
v1.2 canonical Python source contained two different scopes and exported only
the narrower one.

The accepted resolution is:

- `geographic_coverage.locations[].type` describes what a specific named
  location is. It covers physical facilities and administrative units.
- `geographic_coverage.level` describes the administrative or spatial level at
  which the snapshot's data are reported.
- Both may be populated when the snapshot supports both meanings. A table with
  a row for `Baringo District` and observations consistently reported by
  district may identify that location's type as `District` and the coverage
  level as `administrative_area_2`.
- A reporting level alone must not cause the extractor to create named
  locations or copy the level into every location's type. Likewise, the type of
  one named location does not establish the reporting level of the dataset.

The v1.3 field description is:

> The physical or administrative type of a named geographic location
> represented in the snapshot. This field describes what the location is; use
> `geographic_coverage.level` for the administrative or spatial level at which
> the snapshot's data are reported.

This interpretation preserves all four v1.1.1 examples: `Refugee camp`,
`Hospital`, `School`, and `District`. It also agrees with the approved v1.2
concept design, which already described location type as physical or
administrative. The current IATI model similarly separates
[`location-class`](https://reference.iatistandard.org/en/iati-standard/203/activity-standard/iati-activities/iati-activity/location/location-class/),
which includes structures and administrative divisions, from repeated coded
[`administrative`](https://reference.iatistandard.org/en/iati-standard/203/activity-standard/iati-activities/iati-activity/location/administrative/)
identifiers and levels. IATI's more detailed
[`Location Type`](https://reference.iatistandard.org/en/iati-standard/203/codelists/locationtype/)
list includes both facilities and administrative-division feature codes. These
standards support the distinction but do not become mandatory vocabularies for
v1.3.

**Schema Validation impact.** The formal field inventory and object shape are
unchanged. A comparable validation model would receive clearer evidence that
administrative-unit types are representable and may therefore be less likely
to propose a redundant field for them. The size of that effect is unknown, and
this does not revise the completed Validation 3 result.

**Metadata Extraction impact.** The extractor now has an explicit routing
rule: attach `District` to a named location when it expresses what that place
is; use `geographic_coverage.level` when district is the level at which data are
reported; populate both only when each assertion is independently supported.

## Validation plan

Implementation is incremental. The completed items 1, 10, and 11 bundle has
been checked against the following full verification scope, which remains the
standard for later bundles:

1. all accepted Pydantic type, description, and example changes;
2. focused representability cases for each changed field group, together with
   the existing v1.1.1 description and example fidelity checks;
3. Python and exported JSON Schema parity for changed constraints;
4. deterministic regeneration of the JSON Schema and Markdown reference;
5. explicit confirmation that historical Validation 3 inputs and outputs were
   not rewritten; and
6. explicit confirmation that no Schema Validation 4 artifacts or claims were
   introduced as part of the v1.3 implementation.

## Decision log

Items 1, 10, and 11 were approved and implemented as the first v1.3 bundle.
The canonical model now uses plain strings for the six approved semantic field
groups, `CodedTerm` for the five coding-capable groups, and four narrow
normalized-term models. `TemporalExpression.source_text` is optional when
normalized bounds are present. The v1.3 JSON Schema and Markdown reference were
generated separately, and the frozen v1.2 artifacts were not changed. The
historical Schema Validation 3 runner now reads the checked-in v1.2 JSON
directly so later canonical schema versions cannot alter its instrument. Item
15 resolves the `location_type` boundary by distinguishing a named location's
physical or administrative type from the snapshot's reporting level.
