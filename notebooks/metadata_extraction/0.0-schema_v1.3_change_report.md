# Data Snapshot Metadata Schema v1.3 Change Report

**Date:** September 11, 2026
**Status:** Planning and incremental implementation
**Baseline:** Frozen Data Snapshot Metadata Schema v1.2
**Working version:** Data Snapshot Metadata Schema v1.3

## Executive summary

This report tracks the proposed changes arising from the final human QA of
Schema v1.2. The proposed changes are substantial enough to publish as Schema
v1.3. Versioning the result separately preserves the historical interpretation
of Schema Validation 3: that exercise evaluated Schema v1.2 before the
post-validation multi-axis amendment. It did not evaluate the proposed v1.3
semantics, examples, field types, or documentation.

The working principle for this review is:

> Schema v1.3 should preserve the semantic content of Schema v1.1.1, with
> differences limited to approved normalization, standardization, renamed
> fields, and nested relationships.

The review addresses one change at a time. Each decision records its
relationship to the completed Schema Validation 3 conclusion and its expected
effect on metadata extraction before implementation. Approved decisions are
implemented in coherent bundles while their rationale is current. No Schema
Validation 4 or v1.3 rerun is planned. The original Schema Validation 3 results
and report remain attached to the frozen v1.2 instrument.

The next empirical stage is metadata extraction with a newly developed
pipeline. That work will be planned in a separate thread after the v1.3 schema
decisions are complete. This report records extraction implications but does
not design the new pipeline.

## Recommended review sequence

The items should be decided individually, but not strictly in numerical order.
The following order minimizes rework:

1. Establish the cross-cutting representation rules: items 10, 1, and 11.
2. Resolve nested relationships and cardinality: items 8 and 9.
3. Resolve field-specific normalization behavior: items 2, 3, 4, 5, 7,
   and 13.
4. Resolve the location-type semantic boundary separately: item 15.
5. Reconcile the generated and supporting documentation: items 6 and 12.

For each item, the review should produce a short decision record containing:

- the v1.1.1 semantic requirement;
- the current v1.2 representation;
- the proposed v1.3 representation;
- standards or vocabulary evidence, when applicable;
- relationship to the completed Schema Validation 3 result;
- expected effect on metadata extraction;
- the accepted decision and rejected alternatives; and
- the implementation and verification scope.

## 1. Simplify fields without a normalization vocabulary

**Status:** Implemented and verified with items 10 and 11.

Schema v1.2 uses generic `ControlledTerm` in 12 field paths. The proposed rule
is to use plain semantic text when the application has not selected a
vocabulary and has no need to preserve a code or concept URI. The existence of
a broad standards property or ontology is insufficient by itself. A structured
term remains justified when the field may carry a meaningful dataset-specific
code or when a concrete, maintained external vocabulary fits the field's v1.1.1
semantics.

This rule depends on two limited cross-cutting proposals from items 10 and 11:

- `source_text` means literal source-visible wording that itself denotes the
  represented term. It is not a visual clue, contextual evidence, inferred
  classification, paraphrase, or normalized label. A plain-text field instead
  records the schema-level semantic answer and may be directly stated or
  directly supported by visible content.
- The universal five-property `ControlledTerm` should be replaced by the
  smallest value shape justified by each field: plain text, a normalized term
  with a closed local value, or a coded term with optional exact vocabulary
  identifiers. The complete review of the specialized normalized models remains
  under item 11.

### Field proposals

| Current field path | Proposed v1.3 representation | Rationale | Potential impact on Schema Validation | Impact on Metadata Extraction |
|---|---|---|---|---|
| `subject_domains[]` | `NonEmptyText` | The v1.1.1 value is a broad semantic classification. Dublin Core, Schema.org, and SDMX provide ways to represent subjects or subject schemes, but the application has not selected a domain vocabulary that covers the intended corpus. | The subject concept remains covered. The simpler value may reduce representation concerns caused by unexplained normalization properties, but the direction and size are unknown. | The extractor can return `Agriculture` when that domain is supported by visible content even if the word does not appear. It no longer has to invent `source_text` or an unofficial normalized value. |
| `population_group` | `NonEmptyText` | DDI represents a population through textual description and references to a structured Universe; it does not supply one general list containing values such as refugees, children under five, and host communities. | The population concept remains covered, with a representation closer to v1.1.1. | Produces one semantic population description without unsupported term metadata. |
| `intervention_types[]` | `NonEmptyText` | The v1.1.1 scope combines interventions, services, policies, and operational activities. IATI sector, aid-type, and transaction classifications describe narrower dimensions and do not form one equivalent vocabulary. | The intervention concept remains covered. A comparable validation model may find the simpler contract clearer. | Supports inferred semantic labels such as `School Construction` without falsely presenting contextual evidence as `source_text`. |
| `financing.measures[]` | `NonEmptyText` | Project cost, disbursement, financing gap, and budget allocation are different financial quantities or concepts. No single reviewed vocabulary is equivalent to this v1.1.1 field. | The financial-measure concept remains covered; only the value shape becomes simpler. | Reduces object overhead and unsupported codes while preserving all legacy values. |
| `analysis_methods[]` | `NonEmptyText` | Schema.org permits text for measurement techniques, while STATO is a substantial statistics ontology. | `geographic_coverage.locations[].role` | `NonEmptyText` | Country of origin, host country, destination, and reporting location describe relationships in the represented data. | `dimensions[].categories[]` and `dimensions[].category_groups[].categories[]` | Shared coded-term model | SDMX codelists and SKOS concept schemes show why categories may have dataset-specific labels, codes, schemes, and URIs even though no single global category vocabulary exists. Removing an unconstrained normalized value should not remove category semantics. | Allows a visible label alone, or a label plus an exact code and scheme when supplied or verified. The extractor must not manufacture a scheme. |
| `provenance.attributions[].role` | Shared coded-term model | DCAT uses qualified roles and recommends controlled role vocabularies. Requiredness remains an item 8 decision. |
| `geographic_coverage.locations[].type` | Shared coded-term model | IATI publishes a machine-readable Location Type list replicated from US NGA feature-designation codes. It includes physical and administrative feature types relevant to the legacy examples, although it is much more detailed than the application needs. | Retains potential support for normalized feature types; a comparable validation result may be little changed. | Source text remains sufficient. An IATI/NGA code is optional and should be added only by exact lookup or verified enrichment. |
| `financing.instruments[]` | Shared coded-term model | IATI Finance Type is a maintained DAC/CRS transaction classification for grants, loans, and related financial instruments. | `data_collection_methods[]` | Shared coded-term model | DDI maintains separate Mode Of Collection and Type Of Instrument vocabularies. The v1.1.1 field intentionally includes both methods and instruments, so the scheme must identify which vocabulary supplies a code. | Retains explicit method/instrument coverage and credible external normalization. | The extractor returns the stated expression and may attach an exact DDI code through configured lookup. It must not guess which DDI vocabulary applies. |

The proposed coded-term model would retain `source_text`, `code`, `scheme`, and
`uri` only. It would omit the current open-ended `normalized_value`; a code or
URI already identifies the vocabulary concept, and its preferred label can be
resolved from the named scheme. Whether `source_text` or a code must be present
is deferred to item 11 together with enrichment and requiredness rules.

Relevant standards evidence includes the [DDI PopulationType model](https://docs.ddialliance.org/DDI-Lifecycle/3.3/model/composite-types/PopulationType/),
[DDI Mode Of Collection vocabulary](https://rdf-vocabulary.ddialliance.org/ddi-cv/ModeOfCollection/4.0.3/ModeOfCollection.html),
[DDI Type of Instrument vocabulary](https://rdf-vocabulary.ddialliance.org/ddi-cv/TypeOfInstrument/1.1.2/TypeOfInstrument.html),
[DDI Contributor Role vocabulary](https://rdf-vocabulary.ddialliance.org/ddi-cv/ContributorRole/1.0.2/ContributorRole.html),
[IATI Finance Type contract](https://reference.iatistandard.org/en/iati-standard/203/activity-standard/iati-activities/iati-activity/transaction/finance-type/),
[IATI Location Type list](https://reference.iatistandard.org/en/iati-standard/203/codelists/locationtype/),
[SDMX codelist model](https://docs.sdmx.org/en/i1-doc/Sections/Section1/SDMX_2-1_SECTION_1_Framework.html),
[SKOS concept and notation model](https://www.w3.org/TR/skos-reference/), and
[DCAT qualified-role guidance](https://www.w3.org/TR/vocab-dcat-3/#Property:relationship_had_role).

**Schema Validation impact.** These proposals do not alter the conclusion that
no new standalone metadata field was needed. They change the representation of
accepted concepts and may help explain why some v1.2 structures appeared more
elaborate than their underlying semantics required. No rerun is planned.

**Metadata Extraction impact.** Six semantic field groups become plain text.
Five groups retain structured coding because they have a concrete coding use.
This reduces unsupported normalization while preserving exact external or
dataset-specific identifiers where they are meaningful.

## 2. Show normalization through complete worked examples

**Status:** Implemented and verified.

Preserve every original v1.1.1 example expression. For fields with a genuine
normalization structure, add normalized properties only when the mapping is
deterministic. Retain source-only examples when a correct mapping depends on
missing context.

The implementation covers every retained normalization structure:

| Structure | Deterministic paired examples | Examples intentionally left source-only |
|---|---|---|
| Temporal expression | `2015–2020` with year bounds and interval semantics; `January 2024` with month precision | `FY2023`, because fiscal-year bounds depend on the applicable calendar |
| Temporal granularity | Annual, monthly, quarterly, and daily | None among the legacy examples |
| Place and geographic level | ISO alpha-3 country codes for named countries; M49 codes for exact regions; `Country` and `Facility` levels | `Province` and `District`, because their administrative levels vary by jurisdiction; `Latin America`, because M49 `419` denotes Latin America **and the Caribbean** |
| Language | English, French, and Arabic with their BCP 47 primary-language tags | None among the legacy examples |
| Currency and unit | USD, EUR, and JPY currency codes; UN/CEFACT codes for percent and kilometre | `USD` and `People` as unit expressions, because no deterministic unit-code mapping was approved for those examples |
| Statistical form | Count, percentage, rate, and index | `Average`, because it does not by itself distinguish arithmetic, geometric, weighted, or another mean |
| Visualization type | All unambiguous legacy examples, plus inferred-only and explicit `Bar Graph` examples | None among the legacy examples |

Where a concept is illustrated at both root and referenced-type fields, the
worked values are aligned. The v1.1.1 source expressions remain present and in
their original order. Additive examples do not replace them.

**Schema Validation impact.** Validation 3 supplied the complete v1.2 JSON
Schema, including its then-current examples, as model context. The revised
examples belong to v1.3 and do not retroactively change the completed results.
They document one reason the v1.2 and v1.3 model-facing instruments differ.

**Metadata Extraction impact.** Complete examples should teach the extractor
which properties belong together and when normalization is safe. They must not
suggest that optional normalized properties are mandatory or that ambiguous
values should be guessed.

## 3. Correct visualization examples and semantics

**Status:** Implemented and verified.

Use `normalized_value` when the type is inferred directly from visible form.
Use `source_text` only for wording that explicitly names the visualization
form. For example:

```json
{"normalized_value": "bar_chart"}
```

If the snapshot title contains “Respondent Demographic Bar Graph,” a paired
value may be:

```json
{
  "source_text": "Bar Graph",
  "normalized_value": "bar_chart"
}
```

**Schema Validation impact.** This clarifies the intended use of an existing
field. It does not add a concept or change the completed Validation 3
adjudication.

**Metadata Extraction impact.** The extractor can classify visible form without
fabricating source wording. Explicit labels remain available for traceability.

## 4. Define the visualization null fallback

**Status:** Implemented and verified.

The accepted rule is:

- emit a listed `normalized_value` when visual evidence clearly supports it;
- preserve an explicitly written unfamiliar type in `source_text` without a
  normalized value; and
- return `null` when neither condition is satisfied.

The distinction becomes clearer in four cases:

1. A conventional bar chart does not name its form. The visual form supports a
   normalized value, but there is no source text to transcribe:

   ```json
   [{"normalized_value": "bar_chart"}]
   ```

2. A title says `Respondent Demographic Bar Graph`. Both properties are
   supported:

   ```json
   [{"source_text": "Bar Graph", "normalized_value": "bar_chart"}]
   ```

3. A title explicitly says `Waffle chart`, which is not in the current enum.
   The wording can be preserved without forcing a normalized match:

   ```json
   [{"source_text": "Waffle chart"}]
   ```

4. An unfamiliar visual form has no explicit label and cannot be mapped to the
   enum. Neither property has a supported value, so the root field is null:

   ```json
   {"visualization_types": null}
   ```

Under this resolution, review queries distinguish two useful cases:

- `visualization_types is null`: no visualization type could be identified;
- a term with `normalized_value is null`: an explicit unfamiliar label was
  preserved and may justify a vocabulary update.

The Pydantic field description and generated examples now state all four cases.

**Schema Validation impact.** The choice determines how v1.3 describes the
coverage of unfamiliar types. It remains a representation decision within the
existing visualization concept and does not reopen the completed field-inventory
conclusion.

**Metadata Extraction impact.** The rule controls forced enum matches and
whether unfamiliar explicit labels are preserved for later vocabulary review.

## 5. Clarify identifier evidence and enrichment boundaries

**Status:** Implemented and verified.

Identifier values may come from the snapshot or trusted metadata. Schemes,
issuers, and URIs may also come from configured or verified enrichment. The LLM
extractor must not infer or manufacture these values from model knowledge or
from the apparent shape of an identifier.

This boundary is now stated on all four `Identifier` properties and in the
Python README. Pydantic validates the resulting types and URI syntax; evidence
provenance remains an extraction and enrichment responsibility.

**Schema Validation impact.** This is an evidence-boundary clarification within
existing identifier structures. It does not alter the completed conclusion.

**Metadata Extraction impact.** The extractor needs explicit precedence and
provenance rules for snapshot evidence, trusted metadata, configured mappings,
and later verified enrichment.

## 6. Reorganize the generated Markdown reference

**Status:** Approved design; implementation pending.

Keep the validation and serialization section. Organize the Snapshot fields
tables and field-definition subsections by the v1.2/v1.3 modules. Place all
nested models and enums under one `Referenced types` section, with each type one
heading level below it.

**Schema Validation impact.** None. The Markdown is a human review artifact;
Validation 3 used its frozen generated JSON Schema instrument.

**Metadata Extraction impact.** The change improves human implementation and
review. It has no direct model effect unless a future extractor is explicitly
given the Markdown reference.

## 7. Replace `country_code` with `iso3_code`

**Status:** Field rename and alpha-3 syntax implemented and verified; registry
membership enforcement depends on item 13.

Use the ISO 3166-1 alpha-3 country code, such as `PHL`, instead of the current
alpha-2 value `PH`. The field must exclude World Bank three-character region or
aggregate codes that are not ISO country codes. ISO 3166-2 subdivision codes
continue to use an alpha-2 country prefix.

The v1.3 model now exposes only `iso3_code`, requires exactly three uppercase
letters when it is present, and rejects the removed `country_code` property.
Examples use `KEN`, `PHL`, `UGA`, `BFA`, `NER`, `VNM`, and `SSD`. The field
description forbids World Bank aggregate and region codes.

The current deterministic validator still checks syntax rather than registry
membership. Consequently, a plausible three-letter value such as `LCN` fits
the pattern even though it is a World Bank aggregate rather than an ISO 3166-1
alpha-3 country code. Item 13 must decide whether a pinned membership list is
part of core validation or a verified normalization stage.

**Schema Validation impact.** The geographic concept remains present. This is a
normalization change and does not alter the Validation 3 field-inventory
conclusion.

**Metadata Extraction impact.** The extractor and normalizer must map exact
country identities to alpha-3 values and leave the field absent when the
mapping is ambiguous or inapplicable. Region names remain names or use an
appropriate region identifier such as UN M49.

## 8. Review nested requiredness against legacy representability

**Status:** Implemented and verified with item 9.

The v1.2 model rejected several partial representations that v1.1.1 could
express independently:

- a unit, currency, or statistical form without `Variable.name`;
- categories or presentation roles without `Dimension.name`;
- an attribution without an explicit role; and
- a geographic role or location type without a named or source-visible
  location.

The v1.3 rule relaxes a parent label only when the nested child content
still identifies a meaningful schema object. Requiredness should preserve real
relationships, but the schema should not force the extractor to invent a
generic parent such as `Value`, `Measure`, or `Category` merely to retain visible
metadata.

### Implemented requiredness decisions

| Nested object | Proposed v1.3 rule | Reason |
|---|---|---|
| `Variable` | Populate `name` when the measured concept can be identified from the snapshot. Otherwise permit `name: null` only when the variable contains a unit, currency, or statistical form. Analytical roles and axis assignments require a name. | A unit symbol such as `%` states how values are expressed, not what is measured, but it remains meaningful metadata even when the measured concept cannot be identified. A nullable name lets the extractor preserve that evidence without inventing `Percentage`, `Value`, or another placeholder. |
| `Dimension` | Prefer `name` whenever the classificatory concept is explicit or confidently supported. If no defensible name is available, permit an unnamed dimension containing `categories` or `category_groups`; `presentation_roles` may accompany them but cannot be the only content. | Visible category labels can be preserved when the table or chart omits a dimension heading. A bare `row` or `column` role does not say what the dimension represents. |
| `Attribution` | Keep `name` required and make `role` optional. | An explicitly credited agent remains meaningful without a stated role. A role without an agent does not identify an attribution. |
| `GeographicLocation` | Keep an identity requirement, but allow identity through `source_text`, `name`, or an authoritative geographic code or identifier. Reject objects containing only `role` or `type`. | A role or type qualifies a place; it does not identify one. Code-only locations are identifiable, but `{\"role\": \"Host country\"}` does not say which country is the host. The exact code field will be coordinated with item 7. |
| `Unit`, `Currency`, and normalized statistical forms | Retain their current value-level content rules. | Item 8 changes whether the parent variable may be unnamed. It does not permit empty qualifier objects or unsupported normalization. |

### Examples

A chart titled `Households with internet access` displays `%` on its axis. The
title identifies the measured concept and the axis identifies its unit:

```json
{
  "variables": [
    {
      "name": "Households with internet access",
      "unit": {"source_text": "%"}
    }
  ]
}
```

If the snapshot contains only an unlabeled series and `%`, do not use `%`,
`Percentage`, `Value`, or a similar placeholder as `Variable.name`. Preserve the
visible qualifier with an explicitly nullable name:

```json
{
  "variables": [
    {
      "name": null,
      "unit": {"source_text": "%"}
    }
  ]
}
```

An unnamed variable must contain at least one unit, currency, or statistical
form. It cannot contain an analytical role or axis assignment because those
relationships require an identified measured concept. This nullable branch is
also follows OpenAI's [strict Structured Outputs guidance](https://developers.openai.com/api/docs/guides/structured-outputs#all-fields-must-be-required),
which represents unavailable values with `null` rather than forcing a non-null
string.

A table displays rows `Male` and `Female` without a row heading. The proposed
representation is an unnamed dimension with explicit categories:

```json
{
  "dimensions": [
    {
      "categories": [
        {"source_text": "Male"},
        {"source_text": "Female"}
      ],
      "presentation_roles": ["row"]
    }
  ]
}
```

Use an unnamed dimension only when the layout establishes that the labels form
one coherent category set. Do not combine unrelated labels into one anonymous
dimension.

If a footer contains only `© Map Design Unit`, the credited agent may be
preserved without manufacturing `Producer` or another role:

```json
{
  "provenance": {
    "attributions": [
      {"name": "Map Design Unit"}
    ]
  }
}
```

By contrast, the following remains invalid because neither the role nor the
type identifies a geographic entity:

```json
{
  "geographic_coverage": {
    "locations": [
      {"role": "Host country", "type": {"source_text": "District"}}
    ]
  }
}
```

**Schema Validation impact.** A comparable validation model would see
units, currencies, and statistical forms as representable when a variable name
is unavailable; categories as representable when a dimension heading is
absent; credited agents as representable without explicit roles; and places as
identifiable by authoritative codes. No new standalone concept is added, and
the completed Validation 3 result is unchanged.

**Metadata Extraction impact.** The extractor may emit a bounded unnamed
variable to retain a visible unit, currency, or statistical form without
inventing a measured concept. It may likewise emit a bounded unnamed dimension
rather than omit a coherent category set or invent its meaning, retain an
explicitly credited agent without guessing a role, and identify a place through
a trusted code. It must not attach analytical roles or axes to unnamed
variables, or location roles and types to unidentified places.

## 9. Define handling of shared measurement qualifiers

**Status:** Implemented and verified with item 8.

The variable-centric structure needs an explicit rule for one unit, currency,
multiplier, or statistical form that visibly applies to several variables. The
v1.3 rule repeats the complete qualifier on every identified variable to which
it applies.

Do not add a root-level `shared_qualifiers` or inheritance/default mechanism.
Those alternatives would require precedence rules whenever one variable has an
exception and would make each variable incomplete when read independently.
Repetition is more verbose, but the resulting relationship is explicit in both
Pydantic and JSON Schema.

The extraction rules are:

1. Repeat a shared qualifier on every applicable identified variable.
2. Do not attach it to variables for which it does not apply.
3. Preserve the same exact `source_text` in each repeated copy; apply the same
   normalized value or code only when the mapping is justified.
4. If the measured concept is unavailable, an unnamed variable may retain a
   unit, currency, or statistical form under item 8. Do not create multiple
   indistinguishable unnamed variables or invent a placeholder name.
5. Do not use any variable as a shared-default object. That would create an
   undocumented inheritance relationship.

### Shared unit and currency example

A table has columns `Revenue` and `Operating cost` with one heading `US$
millions`. Represent the common qualifiers on both variables:

```json
{
  "variables": [
    {
      "name": "Revenue",
      "unit": {
        "source_text": "US$ millions",
        "multiplier_exponent": 6
      },
      "currency": {"source_text": "US$", "code": "USD"}
    },
    {
      "name": "Operating cost",
      "unit": {
        "source_text": "US$ millions",
        "multiplier_exponent": 6
      },
      "currency": {"source_text": "US$", "code": "USD"}
    }
  ]
}
```

### Shared statistical-form example

A descriptive-statistics table reports `Mean` and `SD` for both `Age` and
`Monthly income`. Repeat both forms on both variables:

```json
{
  "variables": [
    {
      "name": "Age",
      "statistical_forms": [
        {"source_text": "Mean", "normalized_value": "arithmetic_mean"},
        {"source_text": "SD", "normalized_value": "standard_deviation"}
      ]
    },
    {
      "name": "Monthly income",
      "statistical_forms": [
        {"source_text": "Mean", "normalized_value": "arithmetic_mean"},
        {"source_text": "SD", "normalized_value": "standard_deviation"}
      ]
    }
  ]
}
```

If `Age` is reported in years and `Monthly income` in Philippine pesos, the
qualifiers are not shared and must remain attached only to their respective
variables.

**Schema Validation impact.** This primarily documents how existing variable
and qualifier concepts relate. Model-facing descriptions or examples could
make the existing coverage clearer, but no field or formal value type is added
and the completed conclusion is unchanged.

**Metadata Extraction impact.** The extractor receives a deterministic
attachment rule. Output becomes somewhat longer, but every variable remains
self-contained and shared labels are not attached to only the first variable
arbitrarily.

## 10. Apply one `source_text` rule throughout the schema

**Status:** Implemented and verified with items 1 and 11.

Retain the name `source_text` and define it consistently as:

> Exact text or symbol visible in the snapshot that explicitly expresses the
> value represented by this object. Omit it when the value is inferred from
> visual form, structure, or context rather than transcribed.

The rule applies as follows:

| Value type | `source_text` use | Value when no explicit source expression exists |
|---|---|---|
| Plain semantic text approved under item 1 | Not applicable; the field stores the semantic answer directly. | Return the directly supported semantic answer, such as `Agriculture`, without pretending it was transcribed. |
| Statistical form | Preserve an explicit word or symbol such as `Average` or `%`. | Use only the closed `normalized_value` when the form is directly supported but not explicitly named. |
| Visualization type | Preserve explicit wording such as `Bar Graph`. | Use only the closed `normalized_value` when the form is inferred from the visual design. |
| Temporal granularity | Preserve explicit wording such as `Annual`. | Use only the closed `normalized_value` when the granularity is supported by the time sequence or structure. |
| Geographic level | Preserve explicit wording such as `Province`. | Use only the closed `normalized_value` when the level is supported by the snapshot but not explicitly named. Do not use unsupported model-world knowledge. |
| Language | Preserve a language label only when it is itself displayed, such as a language selector reading `English`. | Use the BCP 47 `tag` when the language is identified from the displayed content. |
| Place | Preserve the displayed place expression, such as `The Philippines`. | Use the preferred `name` and applicable codes when the place is directly supported visually or by trusted metadata but not textually named. |
| Unit and currency | Preserve the displayed word, abbreviation, or symbol, such as `%`, `USD`, or `$`. | Do not infer a unit or currency from an unlabeled numeric scale. Add a normalized code only when the visible expression and context support it. |
| Temporal expression | Preserve a complete displayed expression, such as `2015–2020`. | Permit normalized `start`, `end`, `relation`, and `precision` without synthesizing a `source_text` string from separate axis labels. |

The temporal-expression case requires changing `TemporalExpression.source_text`
from required to optional and requiring at least one of `source_text`, `start`,
or `end`. Otherwise an extractor would have to manufacture `2015–2020` when the
snapshot only shows separate yearly axis labels. Exact consistency checks among
`relation`, bounds, and precision remain applicable.

**Schema Validation impact.** This clarifies the evidence semantics of existing
fields. It may help explain model behavior under the v1.2 instrument but does
not change the adjudicated result.

**Metadata Extraction impact.** This is a foundational output rule. It prevents
the extractor from writing paraphrases or inferred category names into a field
presented as source evidence.

## 11. Review properties inherited by specialized term models

**Status:** Implemented and verified with items 1 and 10.

Remove the universal `ControlledTerm`. Replace it with two explicit structural
patterns in addition to the plain text fields approved in item 1:

| Pattern | Properties | Uses |
|---|---|---|
| Purpose-specific normalized term | `source_text`, closed-enum `normalized_value` | `StatisticalFormTerm`, `VisualizationTypeTerm`, `TemporalGranularityTerm`, and `GeographicLevelTerm` |
| Shared coded term | `source_text`, `code`, `scheme`, `uri` | Dimension categories, attribution roles, location types, financing instruments, and data-collection methods |

The four normalized term models should no longer inherit `code`, `scheme`, or
`uri`. Their local enum is the canonical normalized value. If an external
standard provides an equivalent code, the mapping belongs in schema-level
standards metadata or a maintained crosswalk rather than being repeated in
every extracted record.

The shared coded term should not contain `normalized_value`. Its validation
rules should be:

- at least one of `source_text`, `code`, or `uri` must be populated;
- `code` and `scheme` must be populated together; and
- `uri` must be an authoritative URI for the represented concept.

Each purpose-specific normalized term should require at least one of
`source_text` or `normalized_value`. This permits normalized-only inference,
paired source and normalized values, and source-only unfamiliar explicit terms
without accepting arbitrary strings as normalized values.

The implementation should use four small purpose-specific Pydantic models
rather than a public generic base that exposes unrelated properties. Shared
validation may remain an internal helper if it reduces duplication without
changing the generated public schema.

**Schema Validation impact.** This changes the breadth of normalization
properties within accepted concepts. It does not imply that Validation 3 missed
a new metadata field.

**Metadata Extraction impact.** Purpose-specific objects reduce output size and
discourage unsupported codes, schemes, and URIs.

## 13. Align standards claims with actual validation strength

**Status:** Deferred to v1.4. Schema v1.3 performs syntax and relationship
validation only.

Schema v1.3 does not include, download, or invoke an offline normalizer. Its
Pydantic validators check value types, patterns, casing, and relationships such
as the requirement that a `CodedTerm.code` and `scheme` occur together. The
`x-code-list` annotations identify intended authorities; they do not prove that
a supplied value belongs to the named registry.

This boundary permits a syntactically valid but unassigned value to pass. For
example, a three-letter string can pass `iso3_code` validation even if it is not
assigned by ISO 3166-1, and a structurally valid language tag can contain an
unregistered subtag. The v1.3 contract therefore claims syntactic conformance,
not registry membership or successful normalization.

### Affected fields and candidate machine-readable sources

These fields contain normalized values from a named external code list or
registry and would need the planned v1.4 offline normalizer:

| Field path | What v1.3 checks | Candidate authoritative machine-readable source for v1.4 |
|---|---|---|
| `variables[].unit.code` | One to three uppercase letters or digits | [UNECE Recommendation 20](https://unece.org/code-list-recommendations), published as downloadable ZIP/XLS code-list packages |
| `variables[].unit.multiplier_exponent` | A strict integer | [SDMX Global Registry `CL_UNIT_MULT`](https://registry.sdmx.org/items/codelist.html), available through the registry REST service as SDMX-ML or SDMX-JSON and through Excel export |
| `variables[].currency.code` | Three uppercase letters | [SIX ISO 4217 List One](https://www.six-group.com/en/products-services/financial-information/market-reference-data/data-standards.html), published by the ISO 4217 Maintenance Agency as XML |
| `languages[].tag` | BCP 47 composition, ordering, duplication, and casing rules implemented by the model | [IANA Language Subtag Registry](https://www.iana.org/assignments/language-subtags-tags-extensions), published as plain text and XML; v1.4 must also apply BCP 47 composition and preferred-value rules rather than treating complete tags as a flat allowlist |
| `geographic_coverage.scope.iso3_code` and `geographic_coverage.locations[].iso3_code` | Three uppercase letters | [UN M49 country-or-area data](https://unstats.un.org/unsd/methodology/m49/), whose downloadable rows include ISO alpha-3 values and allow country/area rows to be separated from region rows; the official [ISO Country Codes Collection](https://www.iso.org/publication/PUB500001.html) is also available as XML, CSV, and XLS by subscription |
| `geographic_coverage.scope.subdivision_code` and `geographic_coverage.locations[].subdivision_code` | ISO 3166-2-shaped uppercase country prefix and subdivision suffix | [ISO Country Codes Collection](https://www.iso.org/publication/PUB500001.html), published as XML, CSV, and XLS by subscription; acquisition and redistribution terms must be resolved before implementation |
| `geographic_coverage.scope.m49_code` and `geographic_coverage.locations[].m49_code` | Three digits | [UN M49](https://unstats.un.org/unsd/methodology/m49/), with downloadable country/area and geographic-region rows |

Five uses of `CodedTerm` can also carry exact scheme-specific codes or concept
URIs. They are structurally valid in v1.3 without membership checks:

| Field path | Candidate machine-readable source |
|---|---|
| `dimensions[].categories[]` and `dimensions[].category_groups[].categories[]` | The dataset-specific codelist named in `scheme`; there is no single global category list. SDMX schemes can be retrieved from an SDMX registry in SDMX-ML or SDMX-JSON. |
| `provenance.attributions[].role` | [DDI Contributor Role](https://rdf-vocabulary.ddialliance.org/ddi-cv/ContributorRole/1.0.2/ContributorRole.html), published through the DDI controlled-vocabulary linked-data service and API |
| `geographic_coverage.locations[].type` | [IATI Location Type](https://reference.iatistandard.org/en/iati-standard/203/codelists/locationtype/), downloadable as CSV, JSON, or XML |
| `financing.instruments[]` | [IATI Finance Type](https://reference.iatistandard.org/en/iati-standard/203/codelists/financetype/), downloadable as CSV, JSON, or XML |
| `data_collection_methods[]` | [DDI Mode Of Collection](https://rdf-vocabulary.ddialliance.org/ddi-cv/ModeOfCollection/4.0.3/ModeOfCollection.html) and [DDI Type Of Instrument](https://rdf-vocabulary.ddialliance.org/ddi-cv/TypeOfInstrument/1.1.2/TypeOfInstrument.html), published through the DDI controlled-vocabulary linked-data service and API |

`Identifier` values and authoritative URIs are scheme-specific rather than
members of one global registry. Their verification remains configured
enrichment under item 5. Absolute-URI validation proves only URI syntax.

### Proposed v1.4 rejection and retry behavior

An offline normalizer should not ask Luna to try again from scratch whenever a
value fails membership validation. The normalizer has stronger evidence for
deterministic code lookup than the model:

1. Luna extracts source evidence and may propose a normalized value.
2. The offline normalizer validates that value against a pinned local reference
   snapshot.
3. If the visible name or source value has one exact mapping, the normalizer
   fills or corrects the code deterministically and records the correction in a
   pipeline log. No second model call is needed.
4. If no unique mapping exists, the normalized code is removed while the source
   text or semantic name is retained. The pipeline records the unresolved field
   for review outside the metadata schema. If removing the value would leave an
   empty nested object, that object is removed as well.
5. A second Luna call is optional only when snapshot context could resolve the
   ambiguity. It should receive the rejected value, the rejection reason, and a
   bounded list of valid candidates from the local registry. Allow at most one
   retry, validate the result again, and leave the normalized value null if it
   still fails or remains ambiguous.

For example, if Luna returns `{"name": "Philippines", "iso3_code": "PHP"}`,
the offline crosswalk can replace `PHP` with `PHL` without another model call.
If the visible place is only `Congo`, the mapping is ambiguous between `COG` and
`COD`; the normalizer should leave `iso3_code` null unless other snapshot
evidence resolves it. This avoids an open-ended loop and prevents a plausible
model guess from becoming canonical merely because it passes on a later try.

The v1.4 design should use compact pinned allowlists or crosswalks rather than
copies of the standards documents. Each derived file should record its source,
release or retrieval date, checksum, permitted uses, aliases, and treatment of
retired, reserved, and private-use values. Extraction runs should use the local
snapshots and should not fetch registries dynamically.

**Schema Validation impact.** This does not add a metadata concept or change the
completed conclusion. It changes how confidently v1.3 can claim that normalized
values conform to an external standard.

**Metadata Extraction impact.** In v1.3, a plausible but nonexistent value can
pass initial validation. The v1.4 normalizer is expected to correct unique
mappings deterministically, otherwise clear the normalized value and record the
case for review, with only a bounded candidate-assisted model retry when useful.

## 15. Resolve the `location_type` physical-versus-administrative inconsistency

**Status:** Implemented and verified.

The v1.1.1 `location_type` definition and the v1.2 exported field description
say “The type of physical location represented,” but both use `District` as an
example. A district is an administrative unit. The v1.2 `GeographicLocation`
class docstring instead says “Physical or administrative location type,” so the
v1.2 canonical Python source contained two different scopes and exported only
the narrower one.

The accepted resolution is:

- `geographic_coverage.locations[].type` describes what a specific named
  location is. It covers physical facilities and administrative units.
- `geographic_coverage.level` describes the administrative or spatial level at
  which the snapshot's data are reported.
- Both may be populated when the snapshot supports both meanings. A table with
  a row for `Baringo District` and observations consistently reported by
  district may identify that location's type as `District` and the coverage
  level as `administrative_area_2`.
- A reporting level alone must not cause the extractor to create named
  locations or copy the level into every location's type. Likewise, the type of
  one named location does not establish the reporting level of the dataset.

The v1.3 field description is:

> The physical or administrative type of a named geographic location
> represented in the snapshot. This field describes what the location is; use
> `geographic_coverage.level` for the administrative or spatial level at which
> the snapshot's data are reported.

This interpretation preserves all four v1.1.1 examples: `Refugee camp`,
`Hospital`, `School`, and `District`. It also agrees with the approved v1.2
concept design, which already described location type as physical or
administrative. The current IATI model similarly separates
[`location-class`](https://reference.iatistandard.org/en/iati-standard/203/activity-standard/iati-activities/iati-activity/location/location-class/),
which includes structures and administrative divisions, from repeated coded
[`administrative`](https://reference.iatistandard.org/en/iati-standard/203/activity-standard/iati-activities/iati-activity/location/administrative/)
identifiers and levels. IATI's more detailed
[`Location Type`](https://reference.iatistandard.org/en/iati-standard/203/codelists/locationtype/)
list includes both facilities and administrative-division feature codes. These
standards support the distinction but do not become mandatory vocabularies for
v1.3.

**Schema Validation impact.** The formal field inventory and object shape are
unchanged. A comparable validation model would receive clearer evidence that
administrative-unit types are representable and may therefore be less likely
to propose a redundant field for them. The size of that effect is unknown, and
this does not revise the completed Validation 3 result.

**Metadata Extraction impact.** The extractor now has an explicit routing
rule: attach `District` to a named location when it expresses what that place
is; use `geographic_coverage.level` when district is the level at which data are
reported; populate both only when each assertion is independently supported.

## Decision log

Items 1, 10, and 11 were approved and implemented as the first v1.3 bundle.
The canonical model now uses plain strings for the six approved semantic field
groups, `CodedTerm` for the five coding-capable groups, and four narrow
normalized-term models. `TemporalExpression.source_text` is optional when
normalized bounds are present. The v1.3 JSON Schema and Markdown reference were
generated separately, and the frozen v1.2 artifacts were not changed. The
historical Schema Validation 3 runner now reads the checked-in v1.2 JSON
directly so later canonical schema versions cannot alter its instrument. Item
15 resolves the `location_type` boundary by distinguishing a named location's
physical or administrative type from the snapshot's reporting level.
Items 8 and 9 relax nested requiredness only for meaningful partial objects:
unnamed variables retain units, currencies, or statistical forms; unnamed
dimensions retain categories or category groups; credited agents need no role;
and places may be identified by an authoritative code or identifier. Analytical
roles and axis assignments still require a variable name, presentation roles
cannot identify a dimension by themselves, and geographic roles and types
cannot identify a place. Shared measurement qualifiers are repeated on every
applicable identified variable without shared-default inheritance.
Items 2 and 3 add deterministic normalized properties to complete worked
examples while retaining every v1.1.1 expression and keeping ambiguous mappings
source-only. Visualization examples now distinguish inferred form from explicit
source wording. Item 5 records that identifier details require snapshot evidence,
trusted metadata, or configured and verified enrichment rather than model
knowledge. Item 7 renames `country_code` to `iso3_code` and enforces alpha-3
syntax. Item 4 preserves explicitly written unfamiliar visualization types as
source-only terms and uses root `null` when no listed type or explicit unfamiliar
label is supported. Item 13 records that v1.3 performs syntax and relationship
validation only; offline normalization and registry membership validation are
deferred to v1.4.
