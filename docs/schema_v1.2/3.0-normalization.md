# Data Snapshot Metadata Schema v1.2: Normalization Profile

Status: Normalization complete
Date: 2026-09-04

## Purpose

This document specifies the normalization decisions that follow from the
approved semantic crosswalk and concept design. It defines when v1.2 should use
standard formats, identifiers, controlled vocabularies, or source-grounded
text.

The profile is intentionally separate from
[`2.0-concept_design.md`](2.0-concept_design.md). The concept design establishes
what the schema represents and how concepts relate; this document establishes
how their values should be represented consistently. Exact Pydantic classes,
validators, and serialization behavior remain implementation decisions, but
they must enforce the decisions recorded here.

## Normalization policy

### Three representation tiers

1. **Standardized value**: use a recognized external syntax or code list when
   the source meaning can be mapped deterministically. Examples include ISO
   dates, ISO country and currency codes, BCP 47 language tags, and identified
   UN/CEFACT units.
2. **Local controlled value**: use a small v1.2 vocabulary when the application
   needs stable categories but no external vocabulary adequately fits the
   concept. Examples include presentation roles and visualization types.
3. **Open source-grounded value**: preserve the source-visible expression when
   the domain is broad, the vocabulary is context-dependent, or a forced code
   would create false precision. Examples include geographic roles, comparison
   descriptions, and interpretive notes.

An external mapping is optional unless this document explicitly requires it.
The absence of a safe mapping must not prevent representation of visible
metadata.

### General rules

- Normalize only information visible in or directly supported by the snapshot.
- Retain `source_text` when normalization changes the displayed form, resolves
  an abbreviation, or adds a code or identifier.
- Treat `source_text` as a faithful transcription, not raw OCR. Apply Unicode
  NFC normalization, trim surrounding whitespace, and join layout-only line
  breaks; preserve meaningful spelling, capitalization, punctuation, and
  language.
- Do not translate source-visible text as part of normalization.
- Do not infer greater precision than the snapshot supports. In particular, do
  not turn a year into a date, guess the bounds of an unspecified fiscal year,
  or infer a jurisdiction from a place name alone.
- Use the casing and syntax prescribed by the selected standard. Do not alter
  the preserved `source_text` to match the normalized form.
- Associate every general-purpose code or identifier with its scheme. A field
  whose name fixes the scheme, such as `currency.code`, need not repeat it.
- Use absolute URIs conforming to RFC 3986 when an identifier is expressed as a
  URI. Do not manufacture a URI for an identifier that has no authoritative
  URI form.
- Omit unavailable properties rather than emitting empty strings, empty
  objects, placeholder values, or an inferred `unknown` value.
- Preserve source order for ordered content such as panel titles and displayed
  categories. Remove only exact duplicates within the same semantic scope.
- Pin external code-list releases during implementation. Store or document the
  release used by a normalizer so results remain reproducible when external
  lists change.
- Normalization must be possible without live web lookups during extraction.
  Optional enrichment or entity reconciliation may occur later and must not
  overwrite source-grounded values.

## Reusable value patterns

These patterns describe semantics rather than final Pydantic class names.

### Controlled term

A controlled term may contain:

- `source_text`: the displayed expression;
- `normalized_label`: the preferred application or vocabulary label;
- `code`: a code in a named scheme;
- `scheme`: the code-list or vocabulary identifier; and
- `uri`: an authoritative concept URI, when one exists.

`source_text` is sufficient when no deterministic mapping exists. `code` must
not appear without a known scheme unless the containing field fixes the scheme.

### Entity reference

A project, organization, location, or source reference may contain a displayed
`name` and zero or more identifiers. Each identifier preserves its `value` and
may record a `scheme`, `issuer`, or authoritative `uri`. Similar names are not
automatically treated as the same entity.

### Temporal expression

A temporal expression preserves `source_text` and may add normalized `start`
and `end` values, a relation, and precision. The relation uses the local values
`point`, `interval`, `open_interval`, or `as_of`. Precision uses `year`,
`month`, `day`, or `datetime`.

## Standard formats and external identifiers

| Value family | Normalization decision | Authority | Guardrail |
|---|---|---|---|
| Calendar dates and times | Use the ISO 8601 forms `YYYY`, `YYYY-MM`, `YYYY-MM-DD`, and an ISO 8601 datetime with an explicit offset. Represent an interval with separate normalized bounds rather than a free-text range. | [ISO 8601](https://www.iso.org/iso-8601-date-and-time-format.html) | Preserve the original expression and its precision. Do not normalize ambiguous dates or unspecified fiscal years beyond what is deterministic. |
| Country | Use ISO 3166-1 alpha-2 as the primary country code; preserve the displayed country name. | [ISO 3166](https://www.iso.org/iso-3166-country-codes.html) | Do not infer a country code when the place name is ambiguous or historical and has no clearly applicable current code. |
| Country subdivision | Use ISO 3166-2 when the represented administrative subdivision has an exact code. | [ISO 3166](https://www.iso.org/iso-3166-country-codes.html) | Preserve the displayed subdivision type and name; a word such as “province” alone is insufficient to infer a code. |
| World region or statistical area | Use the three-digit UN M49 area code when there is an exact match. | [UN M49](https://unstats.un.org/unsd/methodology/m49/overview/) | Keep nonstandard operational regions as open named places rather than forcing an M49 mapping. |
| Currency | Use the uppercase ISO 4217 alphabetic code. | [ISO 4217](https://www.iso.org/iso-4217-currency-codes.html) | Preserve symbols or displayed names in `source_text`; do not guess among currencies that share a symbol. |
| Language | Use a canonical BCP 47 language tag validated against the IANA Language Subtag Registry. | [RFC 5646](https://www.rfc-editor.org/info/rfc5646/); [IANA registry](https://www.iana.org/assignments/language-subtag-registry/language-subtag-registry) | Do not add an unexpressed region or script subtag. Preserve the displayed language name when present. |
| Unit of measure | Use a UN/CEFACT Recommendation 20 common code when the displayed unit has an exact match. | [UNECE Recommendation 20](https://unece.org/code-list-recommendations) | Retain `source_text`; do not force domain-specific composite units into an approximate code. Currency and multiplier remain separate qualifiers. |
| Unit multiplier | Use the SDMX `CL_UNIT_MULT` exponent when a magnitude such as thousand, million, or billion is explicit. | [SDMX cross-domain code lists](https://sdmx.org/sdmx_cdcl/) | Store the multiplier as a distinct unit qualifier rather than folding it into a currency code. Do not infer a multiplier from chart scale unless explicitly indicated. |
| Temporal frequency | Map exact regular frequencies to SDMX `CL_FREQ`; retain a local value for non-frequency granularity. | [SDMX cross-domain code lists](https://sdmx.org/sdmx_cdcl/) | Do not equate periods such as “as of,” “event-based,” or “irregular” with a regular reporting frequency. |
| URI | Validate absolute identifiers using RFC 3986 syntax. | [RFC 3986](https://www.rfc-editor.org/info/rfc3986/) | Syntax validity does not establish that the URI resolves or identifies the correct entity. |
| Project identifier | Preserve the assigned identifier and identify its scheme or issuer when visible or already known to the application. | Scheme-specific authority, such as an IATI identifier or a development-bank project identifier | Do not reinterpret an internal document label as a project identifier or invent a scheme from the string pattern alone. |

## Local controlled vocabularies

Local vocabularies use lowercase snake-case values. The displayed wording is
retained when it carries information not captured by the normalized value.

### Dimension presentation roles

`dimensions[].presentation_roles` is a closed collection with two values:

- `row`
- `column`

The roles describe the visible table layout. A dimension may have both roles in
an unusual composite, but a role must not be inferred when the layout does not
make it explicit.

### Variable analytical roles

When explicitly stated, a variable may use one or more of:

- `outcome` for outcome, response, or dependent variables;
- `predictor` for predictor, explanatory, or independent variables;
- `instrumental` for instrumental variables;
- `control` for control variables;
- `x_axis` for a variable explicitly assigned to the horizontal axis; and
- `y_axis` for a variable explicitly assigned to the vertical axis.

These values normalize common synonyms but do not infer analytical roles from
position, convention, or statistical knowledge.

### Statistical forms

`variables[].statistical_forms` is an application vocabulary grounded primarily
in [SDMX `CL_STATISTICAL_OPERATION`](https://sdmx.org/wp-content/uploads/CL_STATISTICAL_OPERATION-1.0.docx) and the
[DDI Summary Statistic Type](https://rdf-vocabulary.ddialliance.org/ddi-cv/SummaryStatisticType/2.1.0/SummaryStatisticType.html).
Schema.org's [`statType`](https://schema.org/statType) supplies the
interoperability relationship, but it deliberately accepts a Schema.org
property, text, or an external URI rather than defining a closed code list.

The initial v1.2 values are:

- SDMX-aligned operations: `observed_value` (`OBS`), `count` (`COUNT`),
  `arithmetic_mean` (`MEAN`), `geometric_mean` (`MEANG`), `weighted_mean`
  (`MEANW`), `weighted_value` (`VALUEW`), `median` (`MEDIAN`), `sum` (`SUM`),
  `weighted_sum` (`SUMW`), `minimum` (`MIN`), `maximum` (`MAX`), `range`
  (`RANGE`), `interquartile_range` (`RANGEIQ`), `variance` (`VAR`),
  `standard_deviation` (`SD`), `standard_error` (`SE`),
  `mean_absolute_deviation` (`ADMEAN`), `median_absolute_deviation`
  (`ADMEDIAN`), `skewness` (`SKEW`), `kurtosis` (`KUR`), `lower_bound`
  (`BOUNDL`), `upper_bound` (`BOUNDU`), `score` (`SCORE`), `rank` (`RANK`),
  `index` (`INDEX`), and `rate` (`RATE`);
- DDI-aligned additions: `harmonic_mean` (`HarmonicMean`), `trimmed_mean`
  (`TrimmedMean`), `mode` (`Mode`), `coefficient_of_variation`
  (`CoefficientOfVariation`), `valid_cases` (`ValidCases`), `invalid_cases`
  (`InvalidCases`), `percentage_of_valid_cases`
  (`PercentageOfValidCases`), and `percentage_of_invalid_cases`
  (`PercentageOfInvalidCases`);
- quantile forms: `quartile`, `quintile`, `decile`, and `percentile`, with the
  displayed ordinal or percentile preserved in `source_text` and an exact SDMX
  or DDI code added when available; and
- schema-evidence additions: `ratio`, `proportion`, `percentage`,
  `confidence_interval`, `coefficient`, `p_value`, and `change`.

Use `arithmetic_mean` rather than the less precise `mean`. The last group is
retained because these forms occur in the v1.1 definition or the bounded design
evidence, even though Schema.org, SDMX, and DDI do not jointly provide exact
codes for all of them. Each value should record its external code and scheme
when an exact mapping exists.

If a visible statistical form is outside this list, preserve it as an open
controlled term for review rather than mapping it to a generic `other`. This
allows the vocabulary to evolve from evidence without losing the original
meaning.

### Visualization types

The reviewed sources do not provide a comparably broad standards-body code list
for high-level visualization types. The v1.2 vocabulary is therefore
application-owned but grounded where possible in the established
[Vega-Lite mark vocabulary](https://vega.github.io/vega-lite/docs/mark.html),
which covers primitive area, bar, line, point, rectangular, and geoshape marks
and the composite box-plot, error-band, and error-bar marks.

The initial values are:

- tabular and common charts: `table`, `bar_chart`, `line_chart`, `area_chart`,
  `pie_chart`, `donut_chart`, `scatter_plot`, `bubble_chart`, `dot_plot`,
  `histogram`, `density_plot`, `heatmap`, `box_plot`, `violin_plot`,
  `error_bar`, `error_band`, `radar_chart`, and `treemap`;
- geographic displays: `map`, `choropleth_map`, and `symbol_map`;
- relational, sequential, and explanatory displays: `network_diagram`,
  `flow_diagram`, `timeline`, `diagram`, and `infographic`;
- assembled displays: `dashboard` and `composite_figure`.

Use the most specific recognizable type; use the generic `map` or `diagram`
when a subtype cannot be identified safely. A composite snapshot may list its
visible component types and `composite_figure`. `composite_figure` describes an
assembly of distinct panels or displays, not a single chart that merely layers
several mark types. Do not create panel-to-type mappings under the current flat
panel design.

An unfamiliar but explicit visualization type remains an open controlled term
with its source label. The list should expand through snapshot evidence rather
than by attempting to enumerate every chart supported by a software library.

### Temporal granularity

`temporal_coverage.granularity` uses these preferred local values:

- regular values: `hourly`, `daily`, `weekly`, `monthly`, `quarterly`,
  `semiannual`, and `annual`;
- non-frequency values: `instantaneous`, `event_based`, `multi_year`, and
  `irregular`.

Regular values should also carry their exact SDMX `CL_FREQ` mapping where one
exists. A displayed label that cannot be mapped safely remains in
`source_text` without a normalized value.

### Geographic level

`geographic_coverage.level` uses these preferred values:

- `global`, `world_region`, and `country`;
- `administrative_area_1`, `administrative_area_2`, and
  `administrative_area_3`;
- `locality` and `site`.

The displayed level, such as “province,” is retained. Administrative levels
are normalized only with enough jurisdictional context to establish their
level. Other reporting levels remain open controlled terms rather than being
forced into this list.

## Open or optionally mapped concepts

| Concept | Decision | Optional standards alignment |
|---|---|---|
| `subject_domains` | Open controlled terms. Preserve the displayed or carefully normalized domain label; attach a concept URI only when an exact vocabulary match is available. | SKOS concept schemes; DCAT themes; application-specific taxonomies |
| `dimensions[].categories` and `category_groups` | Preserve displayed labels and explicit source codes. Normalize codes only when their scheme is stated or known from the immediate snapshot context. | SDMX codelists; DDI categories/code lists; SKOS labels and hierarchy |
| `population_group` | Open controlled term because universes and beneficiary groups are domain-specific. | DDI Universe; Schema.org `populationType` |
| `geographic_coverage.locations[].role` | Source-grounded open term. Do not require a closed vocabulary. | Optional scheme mapping when exact |
| `geographic_coverage.locations[].type` | Open controlled term with optional exact code. | IATI `LocationType`; other domain schemes |
| `comparisons` | Source-grounded comparison expressions or named comparators. Preserve a complete relation when shown, such as “Filipinos vs Germans” or “Baseline vs Endline.” Preserve a standalone comparator or benchmark when the focal side is implicit, such as “Europe & Central Asia benchmark”; do not expand it into an invented “current data vs benchmark” statement. This is constrained semantic text, not arbitrary commentary or a duplicate category list. | No required external mapping |
| `provenance.attributions[].role` | Source-grounded open term. Preserve the role expressed by the snapshot rather than constraining it to a local enumeration. Parent-document authors or publishers remain excluded unless the snapshot itself credits them. | Optional PROV-O, Dublin Core, or domain-vocabulary mapping when exact |
| `project.components` | Named source-grounded entities within the project context. | Optional `hasPart` interoperability mapping |
| `intervention_types` | Open controlled terms with optional domain codes. | IATI sector/policy or other domain classifications when semantically exact |
| `financing.measures` | Open controlled terms because project cost, allocation, disbursement, and funding gap are distinct application concepts. | Targeted IATI or SDMX mappings where exact |
| `financing.instruments` | Preserve the displayed instrument; add an IATI `FinanceType` code only for an exact mapping. | [IATI FinanceType](https://reference.iatistandard.org/en/iati-standard/203/codelists/financetype/) |
| `analysis_methods` | Open controlled terms with optional authoritative identifiers. | Schema.org `measurementTechnique`; discipline-specific method vocabularies |
| `data_collection_methods` | Preserve the displayed method and optionally map an exact DDI mode-of-collection value. | [DDI Mode of Collection](https://docs.ddialliance.org/DDI-Lifecycle/3.3/model/composite-types/ModeOfCollectionType/) |

The concepts above are intentionally not closed enumerations. Their diversity
is part of the source evidence, and standards alignment should add structure
without rejecting legitimate values from unfamiliar domains.

## Source-preserving text

The following values receive only the general text normalization rules unless
they participate in one of the explicit mappings above:

- `title`, `document_label`, `subject_summary`, and `panel_titles`;
- variable, dimension, category-group, project, component, source, agent, and
  funder names;
- `comparisons`; and
- `interpretive_notes`.

Notes remain complete source statements. v1.2 does not parse every fact inside
a note into additional metadata fields.

## Field-level decisions

| v1.2 area | Required normalization behavior |
|---|---|
| Identity and discovery | Preserve titles, labels, and summaries as source text. Represent subject domains as open controlled terms with optional identifiers. Keep `panel_titles` ordered and source-visible. |
| Variables | Preserve each variable name. Attach units, currency, multiplier, analytical roles, and statistical forms to the applicable variable. Apply standard codes only when exact. |
| Dimensions and categories | Preserve the dimension/category relationship and source order. Use local `row`/`column` roles. Preserve explicit source codes with their scheme. Keep `category_groups` non-recursive. |
| Temporal coverage | Preserve the complete source expression. Add ISO 8601 bounds, relation, precision, and normalized granularity only when deterministic. |
| Geographic coverage | Preserve names and distinguish overall scope from additional locations. Use ISO 3166 or UN M49 identifiers when exact. Keep role and type open when no safe vocabulary mapping exists. |
| Provenance | Distinguish derivation sources from credited agents. Preserve names; add identifiers only when authoritative. Keep explicit attribution roles open and source-grounded, with optional exact mappings. |
| Project and financing | Preserve project and component names. Keep identifiers scheme-qualified. Normalize currencies and multipliers; use optional IATI mappings for exact instruments. |
| Methods | Preserve method labels. Allow exact mappings to DDI or authoritative method vocabularies without requiring them. |

## Minimal examples

### Temporal interval

```json
{
  "source_text": "Jan–Mar 2016",
  "start": "2016-01",
  "end": "2016-03",
  "relation": "interval",
  "precision": "month"
}
```

### Geographic scope

```json
{
  "source_text": "Republic of the Phil",
  "name": "Philippines",
  "country_code": "PH"
}
```

The displayed abbreviation is preserved; the standardized name and ISO 3166-1
alpha-2 code are added only because the mapping is unambiguous.

### Currency and magnitude attached to a variable

```json
{
  "name": "Project cost",
  "unit": {"source_text": "US$ million", "multiplier_exponent": 6},
  "currency": {"source_text": "US$", "code": "USD"}
}
```

Currency, magnitude, and the displayed unit expression remain distinguishable
even when they occur in one source label.

### Open geographic role

```json
{
  "name": "South Sudan",
  "country_code": "SS",
  "role": {"source_text": "Country of origin"}
}
```

The country identifier is standardized, while the role remains source-grounded
because v1.2 does not impose a closed geographic-role vocabulary.

## Normalization outcome

The normalization phase is complete. v1.2 uses external standards when an
exact, deterministic mapping exists; application-owned controlled vocabularies
when stable categories are required; and open source-grounded values when a
forced mapping would create false precision.

The downstream Pydantic implementation must turn these decisions into reusable
value models and validators without broadening the semantic scope. In
particular, it must:

- separate source text from normalized values and codes;
- validate required external syntax and local controlled values;
- reject unqualified general-purpose codes where the scheme is ambiguous;
- allow open controlled terms in the areas explicitly designated above; and
- generate derived JSON Schema and human-readable documentation from the
  Pydantic source of truth.

Implementation checks should exercise the controlled vocabularies against the
same bounded design snapshots without reopening the approved concept inventory.
After v1.2 is implemented, the planned confirmatory validation exercise should
test whether these normalization rules preserve stable coverage without
requiring new schema concepts.
